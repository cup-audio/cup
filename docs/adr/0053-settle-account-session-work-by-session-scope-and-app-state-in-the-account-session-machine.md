# Settle account session work by session scope and app state in the account session machine

[ADR 0009](0009-use-xstate-for-client-lifecycle-state-machines.md) moved the web app's account auth lifecycle into an XState machine so that the code that starts an async step decides whether its result is still current. The machine and its facade grew rules around that: which reads still count after sign-in, sign-out or an account switch, how sign-out orders its effects, how token refresh runs on the web and in the app shells, and how routes wait for auth. [cup-audio/cup#19](https://github.com/cup-audio/cup/pull/19) introduced the machine and its session scopes, [cup-audio/cup#256](https://github.com/cup-audio/cup/pull/256) (CUP-44) added app-state-driven refresh and the "choose account next" marker, [cup-audio/cup#457](https://github.com/cup-audio/cup/pull/457) moved the machine to the XState v6 beta, and [cup-audio/cup#165](https://github.com/cup-audio/cup/pull/165) and [cup-audio/cup#101](https://github.com/cup-audio/cup/pull/101) made routes depend on it. The [authentication architecture](../architecture/authentication.md#client-session-lifecycle) describes the resulting lifecycle. These decisions were recorded from code comments on 2026-11-23.

## Decision

The [account session machine](../../apps/web-app/src/auth/account-session-machine.ts) owns the lifecycle; the [account session facade](../../apps/web-app/src/auth/account-session.ts) keeps a promise-based API for callers and route loaders.

- **States.** The machine moves through uninitialized → initializing → connected, with a retryable `error` state when initialization fails. `connected` alternates between `ready` (signedOut ⇄ signingIn → signedIn) and signingOut.
- **Session scope.** `ready` is one session scope. Its session reads stop when the scope ends: when a sign-in starts, a sign-out starts, or a signed-in subject changes (a different subject, or none, replaces the signed-in account). A read still in flight then resolves to `null` instead of a stale session, because its result may belong to an account that is no longer signed in. States without a session scope answer reads with fallbacks; while sign-out is clearing the session, or before there is one, there is no session to read. The facade initializes before it sends these.
- **Subscription.** `connected` subscribes to Supabase auth changes once per client. Auth changes reach only the states that handle them, so changes reported during sign-out are ignored without unsubscribing.
- **Sign-in.** Only one OAuth flow runs at a time, because concurrent flows would overwrite each other's PKCE code verifier. A sign-in is refused while signing out or while another sign-in runs. The provider reports the new session before the sign-in call returns. The provider call cannot be recalled, so the caller learns its real outcome even when the session scope ends first and the sign-in actor is stopped. A web sign-in returns before Google does, so only a session that starts shows that the sign-in succeeded.
- **Sign-out.** Sign-out shows signed-out and stops audio immediately, then initializes account auth if needed to clear the stored session; concurrent calls share one sign-out. A sign-out requested before initialization finishes is queued, runs as soon as the client is connected, discards the restored session, and the UI shows signed-out before initialization finishes. The initial restoration keeps cached queries, because route loaders can await it.
- **Choose account next.** Sign-out sets a device-local "choose account next" marker, so the next Google sign-in shows Google's account chooser and the listener can switch accounts ([ADR 0019](0019-sign-in-on-ios-through-supabase-oauth-in-a-system-browser-sheet.md)). The next session that starts clears it; a failed or cancelled sign-in keeps it. It is kept where the session is: local storage on the web, Secure Storage in the shells, but apart from the session's own keys, which sign-out clears ([account session storage](../../apps/web-app/src/auth/account-session-storage.ts)). On the web, Google's authorization parameters carry no `prompt` otherwise, so Google skips its account chooser when it can and a normal sign-in takes one tap less; a fresh sign-in keeps the chooser and adds `max_age=0` ([web adapter](../../apps/web-app/src/platform/account-auth.web.ts)). The platform sign-in option `chooseAccount` asks for that chooser, and `fresh` authenticates again however recent the last authentication was, such as before account deletion ([account auth port](../../apps/web-app/src/platform/account-auth.ts)).
- **Token refresh.** On the web, refresh is left to supabase-js, which follows the page's visibility itself; the web reports no app state, and the web adapter's app-state watcher reports nothing, since supabase-js refreshes only while the page is visible as long as nothing calls `startAutoRefresh` or `stopAutoRefresh`. The machine never calls `stopAutoRefresh` there, which would remove supabase-js's visibility handling until the next page load. Without a session its refresh has nothing to do. In the app shells, refresh runs only in the foreground, as supabase-js does for a visible page: the machine receives `APP_STATE_CHANGED` when the shell comes to the foreground or goes to the background, including its state at the start, and remembers the last report (`undefined` until the shell reports, and always on the web). Calling `startAutoRefresh` also removes supabase-js's own visibility handling, which a WebView's page visibility would otherwise drive. Sign-out stops the shells' auto refresh, so a session that starts in the foreground starts it again. [`watchAppState`](../../apps/web-app/src/platform/account-auth.native.ts) treats a change reported while the state was being read as newer than the state read.
- **Effects.** Effects that touch the network, the platform, the query cache or playback are placeholders in the machine; the facade provides them through `machine.provide(...)` and tests provide fakes. Each placeholder is typed `void`: a placeholder that only throws would infer `never`, which `provide` would then require. Payload-less events are written as `z.object({})`, because the XState docs' `types<{}>()` is an empty type, which the lint forbids.
- **Route access.** Starting the app begins restoring auth without delaying page rendering ([root route](../../apps/web-app/src/routes/__root.tsx)); initialization publishes failures to auth state, so they need not fail navigation. Routes that need a session await it in `beforeLoad`, so a screen never renders before auth settles. The audiobook request waits for any session itself (`requestApi("optional")`), so the [detail view](../../apps/web-app/src/routes/_shell.audiobooks.$conversionId.tsx) needs no `beforeLoad`. Grant-session access must not depend on account auth initializing when no account is signed in. [Recents](../../apps/web-app/src/routes/_shell.recent.tsx) keeps only the subject in its route context, because query options built there would outlive an account switch. Until account auth initializes, the offered sign-in methods are Google only.
- **Failing auth.** [Home](../../apps/web-app/src/routes/index.tsx) treats failing auth as signed out, so it still offers the start form, which needs no account until it is submitted; signing in initializes auth again (`ensureAuthInitialized`) and shows that failure in place. A share that arrives at app start, before the restored session is known, also treats failing auth as signed out ([bootstrap](../../apps/web-app/src/bootstrap.tsx)).

## Consequences

- A late response never reaches a different account: the scope, not the caller, decides whether a read is still current.
- The facade's shown state stays referentially stable and changes only when the shown auth state does.
- Refresh in the shells depends on the platform module reporting app state; the web path depends on never calling the refresh controls.
