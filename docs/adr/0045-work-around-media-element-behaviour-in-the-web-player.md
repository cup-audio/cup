# Work around media element behaviour in the web player

[ADR 0011](0011-serve-one-narration-track-and-play-it-with-one-audio-element.md) plays the narration track on one `<audio>` element in browsers and the iOS app, and makes the element the only playback state. Browsers differ in how that element starts, seeks, fails and reports its duration, and the system's media controls depend on its events. The rules below shaped [`NarrationTrackPlayer`](../../apps/web-app/src/app/player/narration-track-player.ts), [`create-playback.ts`](../../apps/web-app/src/app/player/create-playback.ts), the [audiobook timeline](../../apps/web-app/src/app/player/audiobook-timeline.ts) and the [player host](../../apps/web-app/src/app/player/player-host.ts). They were introduced by [cup-audio/cup#73](https://github.com/cup-audio/cup/pull/73) (one narration track on one element), [cup-audio/cup#176](https://github.com/cup-audio/cup/pull/176) (load a track only when the listener starts it), [cup-audio/cup#228](https://github.com/cup-audio/cup/pull/228) (hold a seek until WebKit knows the duration), [cup-audio/cup#401](https://github.com/cup-audio/cup/pull/401) (native Android player, which split out the media events the system's media controls need) and [cup-audio/cup#508](https://github.com/cup-audio/cup/pull/508) (keep the restored position when a Pause makes Chromium drop the seek to it). These decisions were recorded from code comments on 2026-11-23.

## Decision

- **Start playback before anything is awaited.** `play()` calls `element.play()` synchronously, because Safari refuses audio started after an await. `play` must therefore be called from a user gesture: browsers only then allow audio to start. The one exception is a track URL renewal: when the track URL is older than the renewal age, or the previous playback ended in a media error, Play first requests the audiobook again and sets its newly signed URL at the same position. Only that path plays after an await, which browsers allow on an element an earlier gesture started; if one refuses, the next Play starts the renewed track within its gesture.
- **An interrupted start is no failure.** A pause or a new source interrupts a pending `play()`, which rejects with an `AbortError`; the player ignores it, and ignores any rejection once it is closed.
- **Publish a pause at once.** The element fires `pause` later than the call; the player publishes its snapshot right after `pause()`, so a toggle right after must find it paused already.
- **A source failure before playback is not playing.** Chromium follows the HTML spec's media source failure steps, so a source that fails before playback starts leaves the element unpaused, though it plays nothing. The player's "is playing" accounts for that.
- **Seek only once the duration is known.** WebKit's GStreamer media backend on Linux can fire `loadedmetadata` with a duration of 0 before it has read the track's length; a seek then clamps to that duration, and the backend can settle on a duration of a few milliseconds and end playback at once. The player holds the position to apply and seeks only once the duration is above 0. While the duration is 0, the track plays from the start until the held position is applied. The backend corrects a duration of 0 without firing `durationchange`, so any media event, such as the next `timeupdate`, can be the first to find the duration known. Setting the source starts loading its metadata and resets the element to the start. The element can report its metadata (browsers update `readyState`) before `loadedmetadata` is dispatched, which must then not apply an earlier seek.
- **Keep the target of a seek until `seeked` confirms it.** Chromium can drop a seek that a pause interrupts before the track's first data arrived: the element reports the time as 0 from the pause on, and its `seeked` event lands there. The player remembers where it last asked the element to seek until `seeked` reports that it got there, and asks for the target again when the element landed elsewhere. It asks once only, so an element that keeps landing elsewhere, such as one whose file is shorter than the listed track, is not sent seeking for ever. A finished seek counts as landed within a tolerance, as browsers may snap it to an audio frame. While seeking, the element's time reports where the seek started, not a listening position, so the player reports the seek's target instead.
- **Clamp positions just short of the end.** The timeline clamps a position to the narration track and stops just short of its end: an element sought to its end has ended, and Play would restart it from the beginning.
- **Load only metadata until Play.** The one element loads only the track's metadata for a loaded audiobook; the track itself streams once playback starts.
- **Unloading stops the network.** Removing the source and loading nothing stops the element's network activity.
- **No `crossOrigin` on the element.** The narration track's signed URL carries its own authorization, so the request needs no cookie.
- **Tell the system's media controls only about real changes.** The player reports a play, pause, seek, rate change, wait for data or the end to the media session, never a time update: the system's media controls extrapolate time updates themselves.

## Consequences

- Play from a tap reaches the element within the gesture on every browser; only a renewal plays after an await, and a refusal there costs the listener one more tap.
- A restored position survives WebKit's early zero duration and Chromium's dropped seek, at the cost of the player keeping a held position and a pending seek target beside the element.
- `player-host.test.ts` reproduces these browser behaviours with a fake element, so the order of media events is under the tests' control.
