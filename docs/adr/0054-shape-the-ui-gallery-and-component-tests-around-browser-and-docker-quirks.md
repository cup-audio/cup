# Shape the UI gallery and component tests around browser and Docker quirks

The web app's component tests mount stories of the UI gallery in a Playwright Server that runs in Docker, in Chromium and WebKit ([ADR 0025](0025-run-only-visual-component-tests-in-all-four-browser-projects.md)). Mock Service Worker answers the stories' requests. Media loading, service workers, Docker Desktop's networking, TanStack Router and React's development mode each forced the gallery and the tests into a particular shape. The decisions came from [cup-audio/cup#3](https://github.com/cup-audio/cup/pull/3) (operating-system-assigned ports), [cup-audio/cup#4](https://github.com/cup-audio/cup/pull/4) (gallery thumbnails), [cup-audio/cup#44](https://github.com/cup-audio/cup/pull/44) (mounted story and index), [cup-audio/cup#73](https://github.com/cup-audio/cup/pull/73) (one audio element), [cup-audio/cup#101](https://github.com/cup-audio/cup/pull/101) and [cup-audio/cup#165](https://github.com/cup-audio/cup/pull/165) (route code splitting), [cup-audio/cup#170](https://github.com/cup-audio/cup/pull/170) and [cup-audio/cup#172](https://github.com/cup-audio/cup/pull/172) (view transitions), [cup-audio/cup#198](https://github.com/cup-audio/cup/pull/198) (WebKit in app E2E), [cup-audio/cup#222](https://github.com/cup-audio/cup/pull/222) (WebKit in component tests), [cup-audio/cup#116](https://github.com/cup-audio/cup/pull/116) (account dialog), [cup-audio/cup#312](https://github.com/cup-audio/cup/pull/312) (faster gates), [cup-audio/cup#422](https://github.com/cup-audio/cup/pull/422) (Sentry), [cup-audio/cup#502](https://github.com/cup-audio/cup/pull/502) (narration document on request), and the commits "test(web-app): setup Playwright component testing", "feat(accounts): add social signup and account lifecycle", "feat(playback): add tappable segments and simplify audiobook controls" and "feat(web-app): polish the Recents and detail-view chrome". The [web app README](../../apps/web-app/README.md#component-tests-and-visual-coverage) and the [web app architecture](../architecture/web-app.md) describe the setup. These decisions were recorded from code comments on 2026-11-23.

## Decision

- **Narration tracks are `data:` WAVs.** A story's [narration track](../../apps/web-app/src/ui-gallery/narration-track.ts) is a `data:` URL of silence with the given unit durations, so the gallery's audio element really plays. It is not a path a mock service worker handler answers: browsers seek only in media whose server answers byte ranges, and MSW rebuilds every request in the page without its `Range` header; Chromium plays on from a 200, but WebKit fails the whole track. A `data:` URL never reaches the service worker, and every browser seeks in it. It is not a `blob:` URL: WebKit's GStreamer backend on Linux re-requests ranges of a track while it detects the format, and its blob loader then intermittently delivered bytes from the wrong offset or failed a range at the end of the blob, so about one in five loads failed. The track is an uncompressed WAV rather than an MP3, whose detection re-requested the end of the file more. It is 8-bit unsigned mono PCM at the lowest sample rate Chromium plays, encoded in chunks well below engines' argument limits for `String.fromCharCode`. A track's URL stays the same across responses, as a stored track's would, which also saves encoding it again; the fragment carries the audiobook so tests can tell tracks apart by the audio element's `src`.
- **Gallery reached through the Playwright Server connection.** The [Playwright config](../../apps/web-app/playwright.config.ts) has the browsers reach the gallery through the connection to the Playwright Server: on Docker Desktop for macOS some new connections from the container to the host never complete, and WebKit, unlike Chromium, opens no second connection, so its page loads stalled.
- **A gallery build per run.** Each run starts its own gallery on a port the operating system assigns, so concurrent runs and gallery servers from other checkouts cannot collide with or stand in for it. The tests load a build of the gallery rather than the development server, which transforms modules on request and can push hot updates into a running test (web app README, "Runtime"). The build is React's development build, which keeps the warnings that tests record ([`react-use-warnings.ts`](../../apps/web-app/src/test-utils/react-use-warnings.ts)).
- **Eight workers.** Eight workers passed three consecutive runs in 4.9 min on an M4 Max; 10 and 12 were slower and each failed a test (web app README, "Runtime").
- **Source modules served at their development paths.** Component tests import source modules by the path the development server serves them at, such as `import("/src/platform/share-intake.ts")`, to reach the instance the stories use. The [gallery build](../../apps/web-app/ui-gallery/vite.config.ts) emits every source module as an entry under the same path with a `.js` extension (`createSourceModuleEntries`), and the preview server answers the `.ts` path with it. A source module entry keeps every export, since a test may call any of them.
- **Mounting stories.** Each mount gets its own router that starts at the story's path ([account fixtures](../../apps/web-app/src/ui-gallery/account-fixtures.tsx)): navigating a router an earlier story mounted would let that story's still mounted tree react, and once that tree unmounts the navigation waits for a render that only follows it. Every route's code loads before mounting, so the screen renders as soon as its route lets it; the [landing page story](../../apps/web-app/src/routes/index.story.tsx) loads its split route first, because the chunk download can take longer than the test's URL field lookup waits. TanStack initializes route objects in place, so the [trial story module](../../apps/web-app/src/routes/trials.$grantId.story.tsx) creates one router only. Native share tests use the production API origin, so that story answers the auth configuration locally too. The router renders nothing until the route chunks have loaded, which under a full parallel test run can take longer than a lookup's default second, so the [Recents story](../../apps/web-app/src/routes/_shell.recent.story.tsx) waits longer. A native share test keeps the gallery's own mount: the share plugins hand the URL to share intake and a cold start then opens home, and the gallery's mount keeps the page, and with it the pending URL, where the `mount` fixture would load a new one.
- **Gallery page.** [Tests that block service workers](../../apps/web-app/ui-gallery/main.tsx) mount stories on the index, because the canvas starts the mock service worker; the index renders only after loading every story module, which can finish after a story is mounted, so a mounted story replaces the index and keeps it from rendering. A story that focuses an element, such as one opening a dialog, would scroll the thumbnail grid to its frame, so the gallery makes every `focus` call pass `preventScroll`. Remounting the story frame reloads the story from scratch; changing `src` on a mounted frame would add a history entry, so that going back would navigate the frame only. The thumbnail strip is hidden instead of unmounted, so that showing it again does not reload its frames.
- **Test techniques.** The player host's audio element is never attached to the document, so the reader test keeps the first one created, which is the host's: development mode runs state initializers twice and keeps the first result ([reader test](../../apps/web-app/src/routes/_shell.audiobooks.$conversionId.test.ts)). Focusing a link alone would scroll it into view, and that scroll would close its popover. WebKit in the E2E suite's Docker browser takes longer than the bar's delay to capture the old screen, so the [Recents test](../../apps/web-app/src/routes/_shell.recent.test.ts) delays the transition's update to stand in for that in any browser. The [view transition recorder](../../apps/web-app/src/test-utils/view-transition-recorder.ts) records whether the bar's named element is `position: sticky`, since iOS Safari cuts its snapshot, and whether the document has a snapshot of its own, which would draw stuck bars too low. A cancelled animation, such as one a restarted transition replaces, rejects `finished` with an `AbortError`, so the Recents test waits until no animation is still running instead of for the first set.
- **Screenshot typing.** [`expect`](../../apps/web-app/src/test-utils/component-test.ts) of a `Locator | Page` is a union of page and locator assertions, whose overloaded methods TypeScript cannot call, so the test utilities type `toHaveScreenshot` as the page's overload, whose options are a superset of the locator's.
- **Reader fixture.** The reader stories' local fixture is `renderNarrationDocument`'s HTML, as the listener API serves it, for what `createNarrationDocument` made of the Gates Notes E2E article's source title, source subtitle and body.

## Consequences

- Only the app E2E suite plays a served MP3 track in WebKit; component tests never exercise range requests.
- The worker count was measured against the development server and holds only for that hardware and suite size.
- A new story module that creates more than one router, or a test that changes a story frame's `src`, breaks the gallery's assumptions.
