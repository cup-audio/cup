# Model the player host and position saves as XState machines

[ADR 0009](0009-use-xstate-for-client-lifecycle-state-machines.md) chose XState for client lifecycles with real modes and cancellable async work, and [ADR 0011](0011-serve-one-narration-track-and-play-it-with-one-audio-element.md) removed the browser player's machine, because the one `<audio>` element now is the playback state. On 2026-11-17 the operator asked, in a Claude Code session with no issue of its own, for every implicit state machine in the web app to be found and made explicit with the installed XState; the change that adds this ADR implements it, in the v6 beta (6.0.0-beta.3) that [cup-audio/cup#457](https://github.com/cup-audio/cup/pull/457) moved the web app to the same day. The inventory at commit [4bd4acc1](https://github.com/cup-audio/cup/tree/4bd4acc1adecdca9437406343ee7e72b23ad3a32/apps/web-app/src/app/player) found two hand-rolled lifecycles of the kind ADR 0009 describes, above the element:

- The [player host](../architecture/playback.md#the-player-host) decided whether a track URL renewal was still current by comparing a `Symbol` token after its request, kept a set of waiters for the account's restore, and checked after each await of its takeover of a running Android session whether a load had happened meanwhile. A failed load left the closed previous player as the loaded one.
- [`PlaybackSession`](../../apps/web-app/src/app/player/playback-session.ts) numbered its saves so that only the latest one's failure armed a retry, and kept the armed retry's cancel function and a closed flag beside them.

## Decision

- **The player host is a machine.** [`player-host-machine.ts`](../../apps/web-app/src/app/player/player-host-machine.ts) has a `playback` region (`empty`, `loaded` with `ready` and `renewingTrackUrl`) and an `adoption` region (find what plays, wait for the account, check it, fetch its audiobook, adopt it). Leaving `renewingTrackUrl` cancels the renewal; leaving `loaded` closes the player and clears the system's media controls; any load ends an adoption in progress. `PlayerHost` stays the facade that routes and the mini player call.
- **Position saves are a machine.** [`position-saves-machine.ts`](../../apps/web-app/src/app/player/position-saves-machine.ts) has `writer`, `retry` and `lifecycle` regions. A failure counts only when no newer save is queued behind it, which replaces the save counter. `PlaybackSession` keeps its API and its position conversions.
- **Playback state stays with the players.** The element, or the native player on Android, remains the only state for playing, buffering and the position (ADR 0011). `NarrationTrackPlayer` and the native-backed player keep no machine.
- **What else the inventory found stays as it is.** The account session is a machine already. React component state with no async work of its own (dialog open flags, the navigation progress bar's show delay, the scroll-reach flags, the status announcer) stays React state, as ADR 0009 says. The account conversion submission, whose sign-in and resume refs follow a submission across a sign-in, and the account confirmation run their async work as TanStack Query mutations, which ADR 0009 keeps outside XState. The shared-URL intake and the cover transition hold one pending value each, with no modes, and `watchAppState` in the native auth platform module only drops the state it read once a newer change was reported. The players keep their own flags (a closed player, a failure to show, a position to apply once the duration is known, the native player's stopped session) as fields beside the element or the native player, which ADR 0011 makes the playback state.
- **Ports come in through the machine's input.** Both modules already had a services port that tests fake, so the machines receive it as input instead of through `machine.provide(...)`, which supersedes ADR 0009's rule for a module that has such a port. Like the account session machine, both keep these ports, the players and the callbacks that settle a caller's promise in context, although XState's docs advise keeping unserializable values out of it: neither machine is persisted. Transitions read the clock, the account and the player's snapshot through these ports; they are reads, and effects stay on `enq`. Async work still runs in invoked actors, so the tests drive the real machines through their facades.
- **An effect that throws is reported, not thrown.** An action that throws stops an XState actor for good, which would leave the player ignoring every later control until a reload; browsers throw from some Media Session calls. The machines catch a port's failure, report it to Sentry and carry on. Before, the failure reached the control that caused it.

## Considered options

- **Leave the player host and position saves alone, since ADR 0011 said "no player state machine".** Rejected: that sentence is about playback, which still has no machine; the host's renewal and adoption and the session's retries are the lifecycles ADR 0009 describes, and their stale-result checks were spread across awaits.
- **Convert every stateful module the inventory found.** Rejected: a machine for a dialog's open flag or a single pending value adds indirection without a mode to name, and the mutations' state already lives in TanStack Query.
- **One machine for the host, the players and the saves.** Rejected: the host, the per-load player and the per-load session have different lifetimes; one machine per lifetime keeps each one's states small.

## Consequences

- The playback page's diagrams describe both machines; the machine definitions are authoritative.
- XState v6 transitions only compute, and their effects run after the next snapshot is resolved. Building or adopting a player is therefore an effect that reports what it built back to the machine as an event (`PLAYER_BUILT`, `LOAD_REFUSED`, `LOAD_FAILED`, `ADOPTION_FAILED`), which `playback.loading` waits for. The actor processes that event within the same `send`, so Play still reaches the player within the tap's gesture. A tap made while the host is handling another event is queued behind it, so `loading` keeps what the listener asks for meanwhile (the unit to seek to, Play, Pause, an unload) and applies it once the player is built; the facade's `loadShown`, which returns the new player, throws in that case rather than return the old one. Reading the resume position again after an unload follows the close the same way, through `PLAYER_CLOSED`, and the adoption region waits in `handingOver` until `playback` reports whether the takeover was built.
- Before it leaves `loaded`, a load checks that a listening session can be created on the audiobook (`findSessionRefusal`), so an audiobook whose session is refused leaves the loaded one playing, together with a track URL renewal in progress; the facade rethrows the refusal to the tap. The effect that builds the player also creates the session before it closes the loaded player, for a port that refuses it anyway. A player that cannot be built after the previous one closed leaves nothing loaded; on Android the previous native session then stays open until the next load or a reload.
- `player-host.test.ts` adds cases the old code failed: a refused listening session leaves the loaded audiobook playing (the old code kept a closed player as the loaded one), a refused Media Session call leaves the controls working, and a load during a takeover ends it.
- Pages are told of a change once per event the host handles, after all of its effects, and only when the loaded, shown or unavailable audiobook changed.
