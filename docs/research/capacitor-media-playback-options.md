# Media-playback service and system controls under Capacitor 8

> Historical research, incorporated 2026-11-17. It is the comparison behind the plugins [ADR 0029](../adr/0029-play-the-narration-track-in-the-android-app-with-a-native-media3-exoplayer.md) rejects. It chose no engine; the project first took the own Media3 plugin around the WebView `<audio>`, then, after [#397](https://github.com/patricktree/cup/issues/397), the hand-written ExoPlayer on Android only, with ExoPlayer handling audio focus and headphone disconnects, and kept the WebView `<audio>` on iOS. Built in [#401](https://github.com/patricktree/cup/pull/401); the [playback architecture](../architecture/playback.md#androids-native-engine) has the current state. Repository observations below describe `08b3d00d`; registry facts are from 2026-11-14 and were not reverified. [Original](https://github.com/patricktree/cup/blob/5a5b153b63fcda2536de1337b70e8b62c9e68858/docs/research/capacitor-media-playback-options.md) on the unmerged branch `research/capacitor-media-playback-options`.

Research date: 2026-11-14, for [patricktree/cup#372](https://github.com/patricktree/cup/issues/372) of the [native apps map](https://github.com/patricktree/cup/issues/371). Cup's shells use the installed Capacitor 8.5.3 (`@capacitor/android`, `@capacitor/ios`, `@capacitor/core`, from `pnpm-lock.yaml`), target and compile against SDK 36 with `minSdkVersion` 24 (`apps/mobile-app/android/variables.gradle`), and declare only `INTERNET` in the Android manifest, all at `origin/main` `08b3d00d`. Registry facts come from `registry.npmjs.org` and GitHub on the research date. Source was read from each repository's default branch at the commits named below. Nothing was built, installed or run on an emulator, simulator or device.

Each statement below is marked by how it was established: **source** (read in the plugin's or library's code), **docs** (the vendor's README, changelog or official platform documentation), or **unverified** (neither).

## Question

Which plugins or players could give Cup's Android and iOS apps a `mediaPlayback` foreground service and system media controls under Capacitor 8, and what does each cost? For each: Capacitor 8 support and maintenance, the foreground-service type and permissions, notification and lock-screen controls, `ACTION_AUDIO_BECOMING_NOISY` and audio focus, what it needs from the web player, and for native players what it means for [ADR 0011](../adr/0011-serve-one-narration-track-and-play-it-with-one-audio-element.md), the shared web player, the signed track URL and listening-position saves.

## Answer

Seven options, in two families. The WebView family keeps the web player's single `<audio>` and adds an Android foreground service plus a native media session that relays commands to the page; on iOS it relies on WebKit's own Now Playing and `navigator.mediaSession`. The native family plays the narration track in a native player in both shells.

What stays viable, without choosing the engine:

- **WebView engine, ADR 0011 kept.** `@capgo/capacitor-media-session` and an own Media3 plugin are viable. Capawesome Media Session is viable only if a paid licence is acceptable, and its manifest cannot be checked before buying. `@jofr/capacitor-media-session` is not viable as a dependency (Capacitor 6 peer, unmaintained, GPL), only as a reference: Capgo's plugin has the same Android structure and supports Capacitor 8. Every WebView option leaves headphone-disconnect handling to Cup, and the community plugins also leave the `FOREGROUND_SERVICE_MEDIA_PLAYBACK` declaration to Cup's manifest.
- **Native engine, ADR 0011 partly superseded.** Capawesome Audio Player (paid) and hand-written ExoPlayer plus AVPlayer are viable. `@capgo/capacitor-native-audio` gives no foreground service, so Cup would write the part this ticket is about itself; it is weak on its own.

## WebView options

All four keep the `<audio>` element and its signed track URL exactly as today. The page's work is the same for each: register play, pause and seek handlers, report the playback state and the position state (duration, position, rate) on `timeupdate`, `play`, `pause` and `seeked`, and set title and artwork. On the web and on iOS that is `navigator.mediaSession`, which WebKit enables by default and backs with its own Now Playing publication ([WebView research](webview-audio-playback.md#system-controls-and-navigatormediasession)); on Android, where WebView disables the Media Session API, the same calls go to the plugin. ADR 0011's "system media controls use browser defaults" would be reversed on every platform, which the map allows.

Headphone disconnects stay unhandled on Android for every WebView option: Chromium's `AudioBecomingNoisyReceiver` lives in `components/browser_ui/media`, which Chrome's `MediaSessionHelper` uses; GitHub code search finds no use of it under `android_webview` (unverified beyond that search). None of the community plugins registers for `ACTION_AUDIO_BECOMING_NOISY` (source), so Cup needs its own receiver that pauses the page. Audio focus probably works without native code, because Chromium's content layer creates an `AudioFocusDelegate` for each media session ([WebView research](webview-audio-playback.md#system-controls-navigatormediasession-and-audio-focus)); not checked on a device.

### `@jofr/capacitor-media-session`

**Maintenance.** Latest 4.0.0, published 2024-08-08, the date of the last commit (`c6042078`); peer dependency `@capacitor/core ^6.0.0`; Android build on AGP 8.2.1 and Java 17. 22 open issues, among them "Update to Capacitor 7" (#41), "Is this abandonware now?" (#42, 2025-11-18, unanswered), the missing media-playback permission (#38), headphone disconnect not pausing (#23), `ForegroundServiceDidNotStartInTimeException` crashes (#24) and a receiver-flag `SecurityException` on API 34 (#36). Licence GPL-3.0-or-later.

**Service and permissions (source).** The library manifest declares `FOREGROUND_SERVICE`, an exported `MediaSessionService` with `foregroundServiceType="mediaPlayback"` and a `MEDIA_BUTTON` intent filter, and `androidx.media.session.MediaButtonReceiver`. It does not declare `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, which an app targeting Android 14 or higher must hold for a `mediaPlayback` service ([service types](https://developer.android.com/develop/background-work/services/fgs/service-types#media)); Cup targets 36, so its own manifest would have to add it. The plugin starts the service with `startForegroundService` and binds to it when the page sets the playback state to `playing` or `paused`, and unbinds, which stops it, on `none`; the service calls `startForeground(..., FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK)` once bound. The service therefore stays in the foreground for as long as the page reports `paused`. The plugin config `foregroundService: "always"` starts it at plugin load instead.

**Controls (source).** A `MediaSessionCompat` (`androidx.media:media` 1.6.0) with a `MediaStyle` notification. `setMetadata` sets title, artist, album and the first artwork, fetched with `HttpURLConnection` from an `http(s)` or `data:` URL, so a signed cover URL works without cookies. `setPositionState` sets duration, position and rate. Actions are enabled only for registered handlers: `play`, `pause`, `seekto` (with `seekTime`), `seekbackward`, `seekforward`, `previoustrack`, `nexttrack`, `stop`.

**iOS and web.** The repository has no `ios` directory; per its README, iOS and web are a thin wrapper over the Web API (docs).

### `@capgo/capacitor-media-session`

**Maintenance.** Latest 8.1.11, published 2026-11-13 (`6f7ff5c1`); peer `@capacitor/core >=8.0.0`; first version 7.0.0 on 2025-10-09, 61 versions since; 0 open issues. Not a GitHub fork, but its Android code has the same class names, manifest and lifecycle as jofr's. Licence MPL-2.0.

**Service and permissions (source).** Identical manifest to jofr's: `FOREGROUND_SERVICE`, an exported `mediaPlayback` service with `MEDIA_BUTTON`, the `androidx.media` button receiver, and no `FOREGROUND_SERVICE_MEDIA_PLAYBACK`. Same start on `playing` or `paused`, stop on `none`, and `foregroundService: "always"` option; `startMediaService()` returns early when there is no activity.

**Controls (source).** Android as jofr's (`androidx.media` via `$androidxMediaVersion`). iOS is native: the plugin writes `MPNowPlayingInfoCenter.default().nowPlayingInfo` (title, artist, album, artwork, duration, elapsed time, rate) and registers `MPRemoteCommandCenter` targets. With Cup's `<audio>` playing, WebKit publishes its own Now Playing for the same element, so two publishers would compete on iOS; how they interact is unverified, and Cup may not need the plugin on iOS at all, since `navigator.mediaSession` works there.

### Capawesome Media Session

**Access and maintenance (docs).** `@capawesome-team/capacitor-media-session`, available only to Capawesome Insiders through the private registry `npm.registry.capawesome.io` with a licence key from Polar; the registry answers `401` without one, and the source lives in a private `capacitor-plugins-sponsorware` repository. The public `capawesome-team/capacitor-plugins` repository carries only its README, changelog and an EULA. Version 8.x supports Capacitor 8; the latest changelog entry is 8.4.3, synced on 2026-09-15.

**Service and permissions.** The changelog mentions a "media playback service" (8.4.3: stop it and remove its notification when the plugin is destroyed) and a fix for `ForegroundServiceDidNotStartInTimeException` from native media controls (8.3.1), so Android runs a foreground service. Its type, its permissions and whether the plugin's manifest declares them are not documented: unverified.

**Controls (docs).** `MediaSessionCompat` from `androidx.media` 1.7.1 on Android and `MPNowPlayingInfoCenter` on iOS. `setMetadata`, `setPlaybackState`, `setPositionState`, `registerActionHandler` for play, pause, seek backward and forward, `SEEK_TO`, previous and next track, stop, and `setSeekOffset` since 8.3.0. The README contradicts itself on Android artwork (the FAQ says iOS and web only; the 8.4.3 changelog documents Android support). iOS has the same two-publisher question as Capgo's plugin. Audio focus and headphone disconnects are not documented.

The vendor itself recommends its Audio Player over this plugin for native playback, as "more reliable, especially when the web view is suspended while the app is in the background" (README).

### Own plugin: Media3 `MediaSessionService` with a forwarding `SimpleBasePlayer`

**What Media3 provides (docs).** A `MediaSessionService` declared with the `androidx.media3.session.MediaSessionService` intent filter and `foregroundServiceType="mediaPlayback"`, plus `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_MEDIA_PLAYBACK` ([background playback](https://developer.android.com/media/media3/session/background-playback)). Media3 creates and updates the media notification from the player and session state, and runs the service in the foreground while playing; when the player is paused, stopped or failed "for more than 10 minutes without further user interactions", it leaves the foreground state. From API 33, System UI builds the media controls from the session, not from the notification. Media-session notifications are exempt from `POST_NOTIFICATIONS` ([notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission#exemptions)), so Cup would not have to ask for it. Playback resumption after the service ended needs Media3's `MediaButtonReceiver` and `onPlaybackResumption()`.

**What `SimpleBasePlayer` provides (source, `androidx/media` `release` branch).** A `Player` whose subclass returns an immutable `State` from `getState()` (available commands, playback state, play-when-ready, playlist with duration, position) and handles commands in `handleSetPlayWhenReady` and `handleSeek`, each returning a `ListenableFuture`; `invalidateState()` publishes a change that did not come from a player call ([reference](https://developer.android.com/reference/androidx/media3/common/SimpleBasePlayer)). A Cup subclass would forward play, pause and seek to the page through a plugin event and take its state from plugin calls on the page's media events. It has no audio-focus handling: `handleSetAudioAttributes` throws unless overridden.

**Cost.** All Android code is Cup's: the service, the player, the plugin bridge, a noisy receiver, and audio focus unless WebView's own suffices. Cup knows the parts: the removed `NarrationPlaybackService` (at `0fb4e71d`) extended `MediaSessionService` on Media3 1.11.1 with a `DefaultMediaNotificationProvider`. iOS needs no native code. Unverified: what happens to a notification Play once the service left the foreground after 10 paused minutes and the cached apps freezer froze Cup, and whether starting the service from a notification while backgrounded is allowed.

## Native options

### What a native player means for Cup

- **ADR 0011.** Its "Native players removed" and, in the shells, "one `<audio>` element" would be superseded; the browser keeps the element. One served MP3, the signed URL and "no playing without failed segments" stand.
- **The shared web player.** The web player would get a second engine behind the same timeline: today [`narration-track-player.ts`](../../apps/web-app/src/app/player/narration-track-player.ts) reads playing, buffering, position and duration from the element, and [`PlaybackSession`](../../apps/web-app/src/app/player/playback-session.ts) converts between a listening position and `currentTime`. In the shells both would read native events instead, and the in-app controls would call the plugin.
- **The signed track URL.** A native player requests `https://cup.audio` with the `token` query parameter, which needs no cookie and no CORS or `Cross-Origin-Resource-Policy` ([signed media URL](../architecture/authentication.md#signed-media-url)). Renewal on an in-app Play stays in the page; a lock-screen Play after expiry fails as it does today.
- **Listening-position saves.** Saves run in the page through `CapacitorHttp` ([positions](../architecture/playback.md#listening-positions)). On Android, a foreground service keeps the process, the page and network access alive. On iOS, the `audio` background mode keeps the app process running while a native player plays, but the WebView's page then plays nothing, and whether WebKit suspends its web content process in the background is unverified. The removed native coordinators saved positions natively for that reason (`NarrationPositionStore` at `0fb4e71d`).

### Capawesome Audio Player

**Access and maintenance (docs).** `@capawesome-team/capacitor-audio-player`, Insiders only like Media Session, EULA, private source; latest changelog entry 8.5.1, synced on 2026-09-25. Open issues in the public repository: an equalizer request (#702) and `onEnded` (#657).

**Service and permissions (docs).** Media3 ExoPlayer and session (default 1.6.1, overridable through `variables.gradle`). For media controls the app declares `io.capawesome.capacitorjs.plugins.audioplayer.AudioPlayerService` with `foregroundServiceType="mediaPlayback"` and the Media3 intent filter, plus `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_MEDIA_PLAYBACK`.

**Controls and focus (docs).** `play` with a `metadata` option shows the system controls; `seekBackwardOffset` and `seekForwardOffset` replace the track buttons with seek buttons, documented for audiobooks; `seekTo`, `getCurrentPosition`, `setRate`. "Automatically manages audio focus on Android"; headphone disconnects are not documented, though Media3's ExoPlayer can handle them with one flag. iOS requires the `audio` background mode, which Cup has.

### `@capgo/capacitor-native-audio`

**Maintenance.** Latest 8.5.4, published 2026-11-13 (`0e7f157e`); peer `@capacitor/core >=8.0.0`; one open issue, "Complete Media Session & Lock Screen Control Support" (#236). The older name `@capgo/native-audio` stopped at 8.4.2 (2026-04-20). Licence MPL-2.0. Built for sound effects, music and streams with preloaded asset IDs and queues.

**Service and permissions (source).** No `Service` class in the Android code; the manifest declares only `POST_NOTIFICATIONS`. ExoPlayer (Media3 1.11.1) runs inside the plugin, a `MediaSessionCompat` is created, and a `MediaStyle` notification is posted with `NotificationManagerCompat`, not as a foreground service. The README's Android background section asks the app to declare the permissions and "Start an Android Foreground Service with a media notification" itself; `backgroundPlayback: true` only skips the plugin's pause in `handleOnPause`. So the process would be cached and frozen as today unless Cup adds its own service.

**Controls and focus (source).** Android: title, artist, album, artwork, duration and position, with play, pause, stop, rewind, fast-forward and `ACTION_SEEK_TO`. iOS: `MPNowPlayingInfoCenter` with the same fields and `MPRemoteCommandCenter` play, pause, stop, skip 15 s and `changePlaybackPosition`. `focus: true` requests `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`, pauses on transient loss and stops on permanent loss; there is no noisy handling. `background: true` sets `AudioManager.MODE_IN_COMMUNICATION`, a call mode.

### Hand-written Media3 ExoPlayer and AVPlayer

**Android (source, docs).** A `MediaSessionService` as above around an `ExoPlayer`, whose builder takes `setAudioAttributes(attributes, handleAudioFocus)` and `setHandleAudioBecomingNoisy(true)` (`ExoPlayer.java`, `release` branch), so focus and headphone disconnects are library behavior. Metadata, artwork, duration, position and seek come from the `MediaItem` and the player.

**iOS (docs).** An `AVPlayer` with the `playback` audio session category, `MPNowPlayingInfoCenter` and `MPRemoteCommandCenter`, and interruption handling. Apple documents that AVPlayer pauses automatically when headphones disconnect ([route changes](https://developer.apple.com/documentation/avfaudio/responding-to-audio-route-changes)).

**Cost.** The most code, on both platforms, plus the native-player consequences above. Cup ran this shape until `0fb4e71d`, though per segment with native coordinators, so none of it applies unchanged.

## Limits

No plugin was installed, built against Capacitor 8.5.3 or run; build compatibility of jofr's plugin is inferred from its peer dependency only. Both Capawesome plugins were judged from their public README and changelog alone; their source, manifests and behavior are unverified. Capgo's plugins move fast (both released the day before the research date), so their source may differ by the time Cup decides. The interplay of a native iOS Now Playing publisher with WebKit's, Android WebView's audio-focus behavior, the Android 12 background-start rules for a service started from a notification, and WebKit's suspension of a silent page in a backgrounded app were not checked. No Google Play policy beyond the foreground-service type declaration in Play Console ([service types](https://developer.android.com/develop/background-work/services/fgs/service-types)) was reviewed.
