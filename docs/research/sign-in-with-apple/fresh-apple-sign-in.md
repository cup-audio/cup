# Forcing a fresh Apple sign-in that yields a revocable credential

Research date: 2026-11-22, for [issue #509](https://github.com/cup-audio/cup/issues/509) of the [Sign in with Apple map](https://github.com/cup-audio/cup/issues/465). Apple's developer documentation was read through its DocC JSON (`developer.apple.com/tutorials/data/documentation/<path>.json`, the same text as the rendered pages), Apple Developer Forums threads and Apple Support pages on the research date. Supabase Auth (GoTrue) source was read at [`supabase/auth@10ef107`][auth] (2026-11-17, still the tip of `master` on the research date), supabase-js at [`v2.119.0`][sbjs], the version `apps/web-app` resolves, and Chrome's Auth Tab and Custom Tabs guides on the research date. Repository observations are from `main` at `deea5557`. Nothing was tried on a device or against a real Apple identity; points marked _device check_ are where the sources are silent.

This builds on [Supabase Auth's Apple provider][prior-supabase] ([#468](https://github.com/cup-audio/cup/issues/468)), [Exchanging Apple's authorization code and revoking Apple tokens][prior-tokens] ([#469](https://github.com/cup-audio/cup/issues/469)) and the resolution of [#478](https://github.com/cup-audio/cup/issues/478) (Cup stores no Apple token; an account with an Apple identity confirms deletion with a fresh Apple sign-in, whose credential the Worker revokes).

## Question

How does each platform force a fresh Apple sign-in that hands Cup a credential the Worker can revoke, and what does the person see? On iOS's native sheet: does every request show the sheet and need Face ID, Touch ID or the passcode, and does every completed request return a new `authorizationCode`? On the web and Android through Supabase's web OAuth (Services ID `audio.cup.app.web`): when the browser or Auth Tab still has an Apple session, does Apple sign in without interaction, can Cup force re-authentication, and does every completed flow return a new `provider_refresh_token` that the client can read?

## Answer

- **No silent Apple sign-in exists anywhere.** Apple says "User interaction is required any time a new identity token is requested" and "Obtaining a new identity token on the device requires user interaction" ([Verifying a user][verifying]). Every completed authorization returns "an identity JSON Web Token (JWT), single-use authorization grant code, the state ... and user identifier" ([Authenticating users][authenticating], [Receiving a user's identity token][receiving]), not only the first. So a completed Apple sign-in is always an explicit act by the person, and always carries a fresh code.
- **iOS native sheet.** Each `performRequests()` presents the modal sheet; for an app the person already authorized it is a short confirmation ("Continue with Apple"), not the first-time name and email form ([TN3194][tn3194], [Authenticating users][authenticating]). On a passcode-protected device the confirmation is Face ID or Touch ID, else the passcode, else the Apple Account password ([Authenticating users][authenticating], [Apple Support: How to use Sign in with Apple][support-use]). Only the device's signed-in Apple Account can be used ([Authenticating users][authenticating]). Every success carries a single-use `authorizationCode` valid five minutes, but the property is declared `Data?` and Apple doesn't say when it is `nil` ([`authorizationCode`][native-code], [Token validation][token]); that a returning user gets a new code each time is documented in general terms only (_device check_, as #478 already noted). Apple warns that requesting a new identity token "more frequently than once a day, can result in your request failing due to throttling" ([Verifying a user][verifying]); a deletion confirmation the same day as an ordinary sign-in is therefore a documented, if unquantified, failure mode.
- **Web authorize endpoint.** `/auth/authorize` takes only `client_id`, `redirect_uri`, `response_type`, `response_mode`, `scope`, `state` and `nonce` ([Request an authorization][authorize]); there is no `prompt`, `max_age` or `login_hint`. Even if it had one, Supabase couldn't pass it: GoTrue forwards a client's extra query parameters as `AuthCodeOption`s ([`external.go#L71-L91`][gt-forward]), but `AppleProvider.AuthCodeURL` drops them and adds only `response_mode=form_post` ([`apple.go#L134-L145`][gt-apple-url]). Cup's `googleAuthorizationParams` (`prompt`, `max_age`) has no Apple counterpart. Cup cannot force re-authentication on the web.
- **Web with an existing Apple session.** Apple documents that a returning person sees "A simple confirmation to continue" ([Authenticating users][authenticating]), and the web flow always shows Apple's page where "the user can sign in and accept any terms" ([Request an authorization][authorize]); the only documented response without a code is `user_cancelled_authorize`. On non-Apple devices the person "must log in with their Apple Account, password, and two-factor authentication code" ([Authenticating users][authenticating]), and a trusted browser skips the verification code for 30 days ([Apple Support: How to use Sign in with Apple][support-use]). Whether an existing `appleid.apple.com` session also skips the password, so that the fresh sign-in is a single "Continue" tap, is not documented (_device check_). Either way the flow needs at least one tap on Apple's page.
- **Android can force a full Apple Account sign-in.** Auth Tabs, like Custom Tabs, share cookies with Chrome ([Custom Tabs security FAQ][ct-faq]), so an Apple session from Chrome carries over. An ephemeral Auth Tab (`AuthTabIntent.Builder().setEphemeralBrowsingEnabled(true)`, Chrome 136+, checked with `CustomTabsClient.isEphemeralBrowsingSupported`) keeps cookies "only in the scope of the session's instance" and deletes them on close ([Ephemeral Custom Tabs][ephemeral]), so Apple sees no session and asks for Apple Account, password and verification code. The web app has no equivalent.
- **Every completed web flow returns a new `provider_refresh_token`.** Each Apple callback makes GoTrue exchange Apple's new code and put Apple's tokens on the flow state; the PKCE code exchange returns them as `provider_token` and `provider_refresh_token` ([`external.go#L232-L247`][gt-flowstate], [`token.go#L338-L352`][gt-pkce]). Apple returns a `refresh_token` on every `authorization_code` grant ([TokenResponse][token-response]). The token belongs to the Services ID, so the Worker revokes it with `client_id` `audio.cup.app.web`.
- **How the client reads it.** With `flowType: "pkce"` and `detectSessionInUrl: true` (web, [`account-session.ts`](../../../apps/web-app/src/auth/account-session.ts), [`account-auth.web.ts`](../../../apps/web-app/src/platform/account-auth.web.ts)), supabase-js exchanges `?code=` on initialization, saves the whole session including `provider_refresh_token` to storage and emits `SIGNED_IN` ([`GoTrueClient.ts#L676-L729`][sbjs-init], [`#L2018-L2092`][sbjs-exchange], [`#L5288-L5325`][sbjs-save]). On Android, where the Auth Tab returns the callback URL to the app ([#470](https://github.com/cup-audio/cup/issues/470)), the app calls `exchangeCodeForSession` itself, as iOS does today ([`account-auth.ios.ts`](../../../apps/web-app/src/platform/account-auth.ios.ts)); the returned `session.provider_refresh_token` is the credential. supabase-js says it emits provider tokens "only once immediately after the user signs in" ([`GoTrueClient.ts#L1342`][sbjs-doc]): the next Supabase refresh replaces the stored session with one that has no provider tokens. Cup's confirmation already reads `session.provider_token` from `getFreshAccountSession()` ([`account-confirmation.ts`](../../../apps/web-app/src/data-fetching/account-confirmation.ts)); reading `provider_refresh_token` the same way works until that refresh.

| Platform          | What forces a fresh Apple sign-in                                           | What the person sees                                                                                                                  | Credential for the Worker                                                 |
| ----------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| iOS, native sheet | Every request; no silent path exists                                        | The Apple sheet with "Continue", confirmed by Face ID, Touch ID, passcode or password                                                 | `authorizationCode`, new per success (_device check_); `client_id` App ID |
| Web               | Nothing Cup can add; every completed flow still needs a tap on Apple's page | Apple's page: with a remembered session possibly just "Continue" (_device check_), otherwise Apple Account, password and maybe a code | `provider_refresh_token`, new per flow; `client_id` `audio.cup.app.web`   |
| Android, Auth Tab | Optional ephemeral Auth Tab drops Chrome's Apple session                    | Without ephemeral: as on the web, with Chrome's session. With ephemeral: Apple Account, password and verification code                | `provider_refresh_token`, new per flow; `client_id` `audio.cup.app.web`   |

## iOS: the native sheet

Apple's sample describes the flow: `performRequests()` presents "the Sign in with Apple content to the user in a modal sheet", and if the device has no Apple Account signed in, the person is sent to Settings ([Implementing user authentication][juice]). The sheet's first-time form collects name and email; afterwards the credential state stays `authorized` and "the next time the user authenticates ... they won't be presented with the initial authorization flow", and "the system auth UI [may display] the 'Continue with Apple' button" ([TN3194][tn3194]). Revoking at deletion resets this, so a later sign-in shows the first-time form again.

Confirmation: "With Face ID or Touch ID on passcode-protected devices; With a passcode, if Touch ID or Face ID isn't available; With an Apple Account password, if the passcode isn't set" ([Authenticating users][authenticating]). Apple Support says the same for repeat sign-ins: tap the button and "complete a Face ID, Touch ID, or passcode confirmation" ([Apple Support: How to use Sign in with Apple][support-use]). Apple doesn't document a path where an already-authorized app gets a credential without the sheet; `preferImmediatelyAvailableCredentials` only "tells the authorization controller to prefer credentials that are immediately available on the local device" and isn't described for Apple ID requests ([`preferImmediatelyAvailableCredentials`][prefer]).

What the success returns: "an identity JSON Web Token (JWT), single-use authorization grant code, the state contained in the authorization request, and user identifier" ([Authenticating users][authenticating]). `authorizationCode` is "a short-lived token that the app uses ... as proof that it has authorization to interact with the server", declared `var authorizationCode: Data? { get }` ([`authorizationCode`][native-code]). Apple's DTS post on account deletion and TN3194 don't discuss asking for a new authorization at deletion time ([Forums: handling account deletions][forums-708415], [TN3194][tn3194]); no Apple staff answer found confirms a new code for every returning-user authorization, so this stays a _device check_. Two consequences for the spec:

- **Only the device's Apple Account.** "Native apps only allow the signed-in iCloud user to use Sign in with Apple" ([Authenticating users][authenticating]). If the iPhone's Apple Account isn't the one linked to the Cup account, the native sheet can't produce the right credential, and the Worker's `sub` check (#478) refuses it. The confirmation needs a message for that case; the web app accepts "any Apple Account".
- **Throttling.** "User sessions are long-lived on device, so calling for a new identity token on every launch, or more frequently than once a day, can result in your request failing due to throttling" ([Verifying a user][verifying]). Apple gives no limit. A person who signs in with Apple and confirms deletion minutes later makes two requests in a day; how the sheet fails when throttled is undocumented (_device check_), so the confirmation should treat an Apple error as retryable later.

## Web and Android: Apple's authorize endpoint through Supabase

Apple's `GET https://appleid.apple.com/auth/authorize` documents seven parameters: `client_id`, `nonce`, `redirect_uri`, `response_mode`, `response_type`, `scope`, `state` ([Request an authorization][authorize], [Incorporating Sign in with Apple into other platforms][other-platforms]). Sign in with Apple JS's `ClientConfigI` has the same set plus `usePopup` ([ClientConfigI][clientconfig]). No parameter asks for re-authentication, an account chooser or a maximum authentication age. Apple's identity token claims are `iss`, `sub`, `aud`, `iat`, `exp`, `nonce`, `nonce_supported`, `email`, `email_verified`, `is_private_email`, `real_user_status`, `transfer_sub`, `org_id` and `scopes` ([id_token][id-token]); `auth_time` isn't documented, although GoTrue copies an `auth_time` claim into the identity's custom claims when present ([prior research][prior-supabase]). Whether Apple sets `auth_time`, and to what, is a _device check_; without it, nothing in Apple's response tells a password entry from a remembered session.

GoTrue's `/authorize` deletes `provider` and `scopes`, strips reserved OAuth parameters, and turns every other query parameter into an `oauth2.SetAuthURLParam` ([`external.go#L71-L91`][gt-forward]). That is how Cup's `prompt=select_account` and `max_age=0` reach Google. Apple's `AuthCodeURL(state, args...)` ignores `args` and builds the URL from `response_mode=form_post` alone ([`apple.go#L134-L145`][gt-apple-url]), so on Supabase's hosted flow no extra parameter reaches Apple, documented or not.

What Apple shows: "When the Sign in with Apple UI appears in the opened browser tab, the user can sign in and accept any terms and conditions for your app" ([Request an authorization][authorize]); for a returning person in an app group "a simple confirmation to continue appears" ([Authenticating users][authenticating]). On non-Apple devices "users must log in with their Apple Account, password, and two-factor authentication code" ([Authenticating users][authenticating]); Apple Support adds that on the web the verification step can be skipped for 30 days by trusting the browser ([Apple Support: How to use Sign in with Apple][support-use]). Neither source says whether a remembered Apple web session skips the password as well. A web developer's question about returning users seeing the consent screen again, and asking for `prompt=none`, got only an Apple DTS reply that the behaviour "is unexpected" and a request for a Feedback ID ([Forums: Apple signin web app][forums-750978]). The documented floor is therefore one explicit tap on Apple's page per sign-in; the ceiling, with no Apple session, is Apple Account, password and verification code.

## Android: Auth Tab cookies and the ephemeral option

Chromium's Custom Tabs security FAQ: Custom Tabs, "unlike Android's WebView API, share the same browser state (such as cookies) with the browser app" ([Custom Tabs security FAQ][ct-faq]). An Auth Tab is "a specialized Custom Tab" for authentication ([Auth Tab guide][auth-tab]), and the ephemeral guide says "By default, Custom Tabs share state and features from the user's browser" ([Ephemeral Custom Tabs][ephemeral]). The Auth Tab guide itself doesn't mention cookies; that an Auth Tab shares Chrome's cookies follows from these two statements rather than being stated outright.

An Ephemeral Custom Tab "launches a fully isolated web browser from within an app ... for authentication strategies that shouldn't sync login state with the browser"; "cookies, cached files, history, credentials and other data exist only in the scope of the session's instance" and are deleted when the tab closes ([Ephemeral Custom Tabs][ephemeral]). It needs Chrome 136 or later, is checked with `CustomTabsClient.isEphemeralBrowsingSupported(context, packageName)`, and applies to Auth Tab through `AuthTabIntent.Builder().setEphemeralBrowsingEnabled(true)` as well as to the Custom Tab fallback ([Ephemeral Custom Tabs][ephemeral]). Cup's Auth Tab plugin ([#477](https://github.com/cup-audio/cup/issues/477)) could open the deletion confirmation's Apple sign-in ephemeral, so Apple asks for Apple Account, password and verification code every time. The cost is that trusted-browser state and saved passwords aren't available inside it, and devices without ephemeral support fall back to the shared session. Whether a full re-entry is wanted at all is the spec's decision ([#513](https://github.com/cup-audio/cup/issues/513)); the credential is revocable either way.

## `provider_refresh_token` on every completed web flow

GoTrue, on Apple's `form_post` callback, exchanges Apple's code with the Services ID and the client secret ([`apple.go#L119-L127`][gt-apple-exchange]); in the PKCE flow it stores the provider access and refresh tokens on the flow state ([`external.go#L232-L247`][gt-flowstate]), and the client's `grant_type=pkce` exchange returns them and deletes the flow state ([`token.go#L338-L352`][gt-pkce]). Apple's token endpoint returns `refresh_token` on every authorization-code grant, and only refresh-token validation omits it ([TokenResponse][token-response], [Token validation][token]). Each completed flow therefore yields a new Apple refresh token, issued to `audio.cup.app.web`.

supabase-js, configured as Cup's web app does (`flowType: "pkce"`, `detectSessionInUrl: true`):

1. On initialization it recognizes a PKCE callback (`?code=`) and calls `_getSessionFromURL`, which runs `_exchangeCodeForSession` and removes `code` from the URL ([`GoTrueClient.ts#L676-L729`][sbjs-init]).
2. `_exchangeCodeForSession` posts `auth_code` and the stored `code_verifier` to `/token?grant_type=pkce`, saves the returned session and emits `SIGNED_IN` ([`GoTrueClient.ts#L2018-L2092`][sbjs-exchange]).
3. `_saveSession` writes a deep clone of the whole session, `provider_token` and `provider_refresh_token` included, to the configured storage ([`GoTrueClient.ts#L5288-L5325`][sbjs-save]); on the web that is browser storage under `ACCOUNT_SESSION_STORAGE_KEY`.
4. A later refresh replaces the session with GoTrue's refresh response, which carries no provider tokens; supabase-js documents the provider tokens as emitted "only once immediately after the user signs in" ([`GoTrueClient.ts#L1342`][sbjs-doc]).

So the deletion confirmation can read `session.provider_refresh_token` right after the redirect back, as it reads `provider_token` for Google today; it must do so before the session's first refresh, and it should not rely on it afterwards. Until that refresh, Apple's refresh token sits in browser storage; the confirmation sends it at once and the Worker revokes it, so its exposure ends there. Native apps (`detectSessionInUrl: false`, [`account-auth.native.ts`](../../../apps/web-app/src/platform/account-auth.native.ts)) get the same session from their own `exchangeCodeForSession` call. In the implicit flow GoTrue would put the token in the redirect URL instead ([`external.go#L286-L295`][gt-implicit]); Cup uses PKCE.

## Device checks left open

- iOS: whether every returning-user authorization returns a non-`nil`, new `authorizationCode` (already open from #478).
- iOS: how a throttled request fails, and after how many requests.
- Web and Android: whether a remembered Apple web session skips the password, leaving only "Continue".
- Whether Apple's identity token carries `auth_time`, and whether it reflects the actual authentication.
- Android: whether an ephemeral Auth Tab on the deletion confirmation behaves as Chrome's guide says on Cup's supported devices.
