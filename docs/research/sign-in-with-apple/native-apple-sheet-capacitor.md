# Native Apple sheet in Cup's Capacitor 8 iOS shell

Research date: 2026-11-18, for [cup-audio/cup#467](https://github.com/cup-audio/cup/issues/467) under the map [cup-audio/cup#465](https://github.com/cup-audio/cup/issues/465). Question: which ways exist to show `ASAuthorizationAppleIDProvider`'s native sheet from Cup's Capacitor 8 iOS shell and return the identity token, the authorization code, and the first-sign-in name and email to the web app, so that the web app can hand Supabase an ID token bound to a nonce? Each option is judged on Capacitor 8 and Swift Package Manager (SPM) support, nonce handling, cancellation and error reporting, whether it exposes the authorization code, maintenance, and fit with `apps/mobile-app` and the iOS adapter in `apps/web-app/src/platform`.

The plugin sources were read from the npm tarballs of the latest published versions on the research date, and their repositories through the GitHub API; Supabase Auth's source at `master` (last change to the file 2026-08-10) and Supabase's Apple guide (last changed 2026-10-22); Apple's documentation pages on the research date. Nothing was built or run on a device. Points marked _unverified_ are inferences the sources did not state directly.

## Answer

Two options work with Cup today: Capawesome's `@capawesome/capacitor-apple-sign-in` 0.1.5, and a hand-written `AppleSignIn` plugin next to `WebAuthenticationPlugin.swift`. `@capacitor-community/apple-sign-in` does not resolve under Capacitor 8 with SPM, and Capgo's `@capgo/capacitor-social-login` would link the Facebook and Google Sign-In SDKs into the iOS app and keep Apple's ID token in `UserDefaults` unless configured otherwise.

The recommendation is the **hand-written plugin**, with Capawesome's as the fallback if the team would rather not own Swift. The native part is about 80 lines, the same shape as `WebAuthenticationPlugin`: it is registered in `MainViewController.capacitorDidLoad()`, needs no npm package, no `cap sync` change and no `ios.includePlugins` entry, and adds nothing to Android. It can reject a second concurrent call with `IN_PROGRESS`, reject a credential without an identity token instead of resolving an empty string, and, like Android's `FakeGoogleSignInPlugin`, get a debug-only fake that the mobile E2E suite can drive, since the real Apple sheet cannot be automated. Capawesome's plugin is a correct, small, maintained implementation of the same calls, but it does not guard against concurrent calls, resolves empty strings for a missing token, and as an npm package it would also be built into the Android app unless `android.includePlugins` is introduced.

Whatever plugin is used, the nonce works as it does for Google on Android: the web app generates a random raw nonce, gives the plugin its **SHA-256 hex digest**, which Apple puts into the identity token's `nonce` claim, and passes the **raw** nonce to `signInWithIdToken({ provider: "apple", token, nonce })`, which hashes it and compares. The nonce code in `account-auth.android.ts` can be shared. Supabase's Apple provider must list the bundle ID `audio.cup.app` among its client IDs, after the web Services ID.

## 1. What the sheet returns and what Supabase checks

### Apple's API

`ASAuthorizationAppleIDProvider().createRequest()` creates an `ASAuthorizationAppleIDRequest`, whose `requestedScopes` take `.fullName` and `.email` and whose `nonce` is "a string value to pass to the identity provider. You can verify this value with the identity token provided as part of a successful ASAuthorization response". An `ASAuthorizationController` performs it, with a delegate for the result and a `presentationContextProvider` that names the window the sheet appears over. Sources: [`nonce`](https://developer.apple.com/documentation/authenticationservices/asauthorizationopenidrequest/nonce), [`presentationContextProvider`](https://developer.apple.com/documentation/authenticationservices/asauthorizationcontroller/presentationcontextprovider), [Implementing user authentication with Sign in with Apple](https://developer.apple.com/documentation/authenticationservices/implementing-user-authentication-with-sign-in-with-apple).

On success the credential is an `ASAuthorizationAppleIDCredential` with `user` (the stable, team-scoped identifier), `identityToken` (a JWT, as UTF-8 `Data`), `authorizationCode` ("a short-lived token ... as proof that it has authorization to interact with the server", UTF-8 `Data`), `email` and `fullName`. The full name "is not included in the user's identity token"; Apple passes it only to the app. Apple's REST API states that the authorization code "is single-use only and valid for five minutes". Sources: [`authorizationCode`](https://developer.apple.com/documentation/authenticationservices/asauthorizationappleidcredential/authorizationcode), [`identityToken`](https://developer.apple.com/documentation/authenticationservices/asauthorizationappleidcredential/identitytoken), [`fullName`](https://developer.apple.com/documentation/authenticationservices/asauthorizationappleidcredential/fullname), [Generate and validate tokens](https://developer.apple.com/documentation/signinwithapplerestapi/generate-and-validate-tokens).

Name and email arrive only on the first authorization: Supabase's guide says "Apple only provides the user's full name during the first sign-in attempt ... All subsequent sign-ins return `null`", and Apple's guide says an app "only requests information the first time the user logs in". The email stays in the identity token's `email` claim on later sign-ins, which is how Supabase reads it; the name does not. Sources: [Supabase: Login with Apple](https://supabase.com/docs/guides/auth/social-login/auth-apple), [Authenticating users with Sign in with Apple](https://developer.apple.com/documentation/signinwithapple/authenticating-users-with-sign-in-with-apple).

Cancellation surfaces as `ASAuthorizationError.Code.canceled`, "The user canceled the authorization attempt." Source: [`ASAuthorizationError.Code.canceled`](https://developer.apple.com/documentation/authenticationservices/asauthorizationerror-swift.struct/code/canceled).

The app needs the `com.apple.developer.applesignin` entitlement, which Xcode adds with the Sign in with Apple capability. Source: [Sign in with Apple entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.applesignin). Cup's iOS project has no `.entitlements` file yet (checked in `apps/mobile-app/ios/App`); adding the capability creates one and needs a provisioning profile with the capability for team `4GQ2V3WJW8`, which belongs to the map's release-signing ticket.

### Supabase's checks

`signInWithIdToken` with `provider: "apple"` reaches Supabase Auth's `token_oidc.go`. For Apple it accepts as audiences every entry of the Apple provider's client IDs plus the optional `IosBundleId`, so the token's `aud`, Cup's bundle ID `audio.cup.app`, must be in that list. The nonce check, unless the provider skips it: if exactly one of the request and the token carries a nonce, it fails ("Passed nonce and nonce in id_token should either both exist or not."); if both do, it computes `fmt.Sprintf("%x", sha256.Sum256([]byte(params.Nonce)))` and fails with "Nonces mismatch" when that differs from the token's claim. The supabase-js type says the same: "If the ID token contains a `nonce` claim, then the hash of this value is compared to the value in the ID token." Sources: [`internal/api/token_oidc.go`](https://github.com/supabase/auth/blob/master/internal/api/token_oidc.go), `SignInWithIdTokenCredentials` in `@supabase/auth-js` 2.119.0 `dist/module/lib/types.d.ts`.

So the plugin must give Apple the lowercase hex SHA-256 of the raw nonce, and the adapter must give Supabase the raw nonce. Supabase's own Flutter example does exactly this (`hashedNonce = sha256.convert(utf8.encode(rawNonce)).toString()` to Apple, `rawNonce` to `signInWithIdToken`). None of the plugins hashes; all pass the given string to `request.nonce` unchanged, so hashing stays in the web app, as in `account-auth.android.ts`. Source: [Supabase: Login with Apple, Flutter tab](https://supabase.com/docs/guides/auth/social-login/auth-apple).

Supabase's guide also says that when a project uses both the web OAuth flow and native sign-in, the web Services ID must be the **first** client ID, because the web flow uses the first one, while native `signInWithIdToken` accepts any entry. Native-only use needs no client secret rotation; the web flow does (every six months). Supabase does not take the name from the token; the guide's recommendation is to call `updateUser({ data: { full_name, given_name, family_name } })` after the first sign-in when the credential carries a name. Source: [Supabase: Login with Apple](https://supabase.com/docs/guides/auth/social-login/auth-apple).

## 2. `@capacitor-community/apple-sign-in`

- **Version and Capacitor 8.** Latest 7.1.0, published 2025-10-02, which added SPM support (#127). Its peer dependency is `@capacitor/core >=7.0.0`, but its `Package.swift` declares `.package(url: "https://github.com/ionic-team/capacitor-swift-pm.git", from: "7.0.0")`, which SwiftPM reads as `7.0.0..<8.0.0`. Cup's generated `CapApp-SPM/Package.swift` pins `capacitor-swift-pm` `exact: "8.6.2"`, so the graph cannot resolve. Issue [#133 "feat: capacitor 8"](https://github.com/capacitor-community/apple-sign-in/issues/133) (opened 2025-12-16) quotes exactly this resolver error. Capacitor 8 PR [#132](https://github.com/capacitor-community/apple-sign-in/pull/132) was closed unmerged, [#137](https://github.com/capacitor-community/apple-sign-in/pull/137) (2026-02-10) is open, and the maintainer wrote in #133 that he "won't be able to do any work on Capacitor Community repositories during working hours anytime soon". Last commit on `master`: 2025-12-05.
- **Source** (`ios/Sources/SignInWithApple/Plugin.swift`, 7.1.0): sets `request.nonce = call.getString("nonce")` verbatim; sets no `presentationContextProvider`; stores the call ID in `UserDefaults()` to find the saved call later; force-unwraps `identityToken!` and `authorizationCode!`; on error calls `call.reject(error.localizedDescription)` without a code, so the web app could tell a cancellation only by a localized message. It returns `user`, `email`, `givenName`, `familyName`, `identityToken`, `authorizationCode`. The TypeScript options require `clientId` and `redirectURI`, used only on the web.
- **Verdict.** Not usable with Capacitor 8 without a fork, and its error reporting would need changes anyway.

## 3. `@capawesome/capacitor-apple-sign-in`

- **Version and Capacitor 8.** Latest 0.1.5 (2026-11-07), MIT, from the public [`capawesome-team/capacitor-plugins`](https://github.com/capawesome-team/capacitor-plugins/tree/main/packages/apple-sign-in) monorepo. Peer `@capacitor/core >=8.0.0`; README compatibility table "0.1.x | >=8.x.x | Active support"; CocoaPods and SPM. `Package.swift` requires `capacitor-swift-pm` `from: "8.0.0"` and iOS 15, matching Cup's iOS 15 deployment target. Release history: 0.1.0 on 2026-03-01, then 0.1.1 (iOS: surface the underlying error code, run on the main thread, retain the controller), 0.1.4 (iOS: remove an SPM test target that made the package unresolvable), 0.1.5 (Android only). Same author and repository as `@capawesome/capacitor-google-sign-in`, which Cup already uses on Android.
- **Source** (`ios/Plugin/AppleSignIn.swift`, `AppleSignInPlugin.swift`, 0.1.5): builds the request on the main queue with the requested scopes (`EMAIL`, `FULL_NAME`) and sets `request.nonce` to the given string verbatim; retains the controller; presentation anchor is `bridge?.webView?.window`. On success resolves `authorizationCode`, `idToken`, `user`, `email`, `givenName`, `familyName` (null when absent) and `realUserStatus`. `authorizationCode` and `idToken` fall back to an empty string when Apple returns no data, rather than failing.
- **Errors.** `ASAuthorizationError.canceled` becomes the code `SIGN_IN_CANCELED` (exported as `ErrorCode.SignInCanceled`); any other `ASAuthorizationError` is rejected with its numeric raw value as a string code, and other errors without a code.
- **Concurrency.** A second `signIn` while one runs replaces the stored completion, so the first call would never settle (read from the source; not run).
- **Fit.** `initialize` is a no-op on iOS. Cup would add the package to `apps/mobile-app` and `apps/web-app`, list it in `ios.includePlugins` in `capacitor.config.ts`, and import it lazily in `account-auth.ios.ts`, as `account-auth.android.ts` does with the Google plugin. Cup's configuration filters only iOS plugins, so the package's Android code (a WebView OAuth flow to Apple) would be built into the Android app too unless an `android.includePlugins` list is added.

## 4. `@capgo/capacitor-social-login`

- **Version and Capacitor 8.** Latest 8.7.11 (2026-11-13), MPL-2.0, peer `@capacitor/core >=8.0.0`. Its `Package.swift` depends on `capacitor-swift-pm` 8.x, `facebook-ios-sdk` 18 and `GoogleSignIn-iOS` 9. The README's "Dynamic Provider Dependencies" section says providers set to `false` under `plugins.SocialLogin.providers` are not bundled; a `capacitor:sync:before` hook (`scripts/configure-dependencies.js`) rewrites the package's dependency files for that, so `cap sync` edits a file inside `node_modules`.
- **Source** (`ios/Sources/SocialLoginPlugin/AppleProvider.swift`, 8.7.11): sets `request.nonce` verbatim; requests name and email by default; caches the name per user in `UserDefaults` and replays it on later sign-ins; decodes the email from the token. Without `useProperTokenExchange: true` it returns the authorization code as `accessToken.token` ("legacy mode") and `authorizationCode: nil`; with it, `authorizationCode` is set. Without a `redirectUrl` it persists `idToken` in `UserDefaults` under `AppleProviderSharedPrefs_0eda2642`.
- **Errors.** `SocialLoginPlugin.swift` rejects with `USER_CANCELLED` when `isUserCancelledError` matches, which checks the error domains and codes but also whether the description contains "cancelled" or "canceled".
- **Verdict.** Works, but brings two third-party SDKs and a `node_modules`-rewriting hook for one system API, and writes an unprotected Apple ID token to `UserDefaults`, outside the Keychain where Cup keeps its session.

## 5. A hand-written plugin next to `WebAuthentication`

Cup already has three app-local plugins on iOS, `WebAuthenticationPlugin`, `CrashReportingPlugin` and `WebViewProcessLossPlugin`, registered in `MainViewController.capacitorDidLoad()` with `bridge?.registerPluginInstance(...)`, which is the pattern Capacitor 8's docs describe for custom code in an app. Source: [Capacitor 8: Custom native iOS code](https://github.com/ionic-team/capacitor-docs/blob/main/versioned_docs/version-v8/main/ios/custom-code.md); local `apps/mobile-app/ios/App/App/MainViewController.swift`.

A sketch of what an `AppleSignInPlugin.swift` would hold, following `WebAuthenticationPlugin.swift`:

- `jsName = "AppleSignIn"`, one method `signIn({ nonce })`, conforming to `ASAuthorizationControllerDelegate` and `ASAuthorizationControllerPresentationContextProviding` (anchor `bridge?.viewController?.view.window`, as `WebAuthenticationPlugin` uses).
- On the main queue: reject `IN_PROGRESS` if a controller is running; else request `[.fullName, .email]`, set `request.nonce` to the given hashed nonce, keep the controller until it completes.
- Resolve `{ identityToken, authorizationCode, user, email, givenName, familyName }`; reject `FAILED` when the token or code is missing, `CANCELED` for `ASAuthorizationError.canceled`, `FAILED` with the error otherwise.
- A debug-only fake, like Android's `FakeGoogleSignInPlugin`, registered instead under the test API origin, that asks the fake auth provider for an Apple-style ID token carrying the hashed nonce, so the mobile E2E suite covers the adapter, Secure Storage and the Worker's token check without Apple. With a third-party npm plugin, replacing it by a fake of the same `jsName` on iOS would have to be tried first (_unverified_).

The web side in `account-auth.ios.ts` would register the plugin with `registerPlugin`, as it does `WebAuthentication`, reuse the Android adapter's nonce generation, call `signInWithIdToken({ provider: "apple", token: identityToken, nonce })`, map `CANCELED` to `SignInCancelledError`, and, when a name came back, call `updateUser` with it. The authorization code is single-use for five minutes, so whatever the map decides about custody of Apple's refresh token, the adapter has to send the code to the Worker right after the sheet closes.

The cost is owning the Swift: about the size of `WebAuthenticationPlugin.swift`, on an API that has been stable since iOS 13, against a dependency that already wraps the same calls. The plugin adds no npm package, no `ios.includePlugins` entry and nothing to the Android build.

## Open points for the map

- **Supabase configuration.** Add the Apple provider with `audio.cup.app` in its client IDs, after the web Services ID; keep the nonce check on. Belongs to the Terraform and web tickets.
- **Entitlement and signing.** The capability creates the app's first `.entitlements` file and needs a provisioning profile with Sign in with Apple for team `4GQ2V3WJW8`; the Share Extension does not need the capability (_unverified_, it never signs in).
- **Name custody.** Where the first-sign-in name lands (Supabase user metadata via `updateUser`, or Cup's own profile) is for the login and account tickets; the plugin only returns it.
- **Simulator.** Whether the native sheet works on the iOS Simulator with an Apple Account signed in was not tested here; the physical-device check in CUP-45's acceptance criteria stays the real proof.
