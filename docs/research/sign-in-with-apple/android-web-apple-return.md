# Returning to the Android app from a web Apple sign-in without App Links

Research date: 2026-11-18, for [issue #470](https://github.com/cup-audio/cup/issues/470) of the [Sign in with Apple map](https://github.com/cup-audio/cup/issues/465). Repository observations are from `main` at `7cf2a405`, with `@supabase/supabase-js` `2.119.0`, Capacitor `8.6`, `@capacitor/app` `8.1` and no `@capacitor/browser` installed. Web sources and GitHub sources were read on the research date; versions read are named where they matter (Supabase Auth `v2.198.0` source on `master`, supabase-js at tag `v2.119.0`, `@capgo/capacitor-social-login` `8.7.11`). No Apple, Supabase or Google setting was read or changed, and nothing was built or run on a device. Points marked _unverified_ need a prototype.

## Question

If Cup's Android app offers Sign in with Apple through Supabase's OAuth flow, how does that flow return to the app now that the app claims no App Links ([ADR 0017](../../adr/0017-keep-trial-links-out-of-the-mobile-apps.md))? The ticket asks about a custom URL scheme with Custom Tabs or an external browser, Supabase's redirect allow-list, PKCE verifier storage in the shell, Apple's restrictions on return URLs (Apple redirects to Supabase, which redirects on), and how comparable Capacitor apps do it.

## Answer

- **There is no native Apple sign-in on Android; a browser flow is the only path.** Apple ships AuthenticationServices only on its own platforms, and Supabase's Apple guide says "On Android, Sign in with Apple is not natively supported" and points every non-Apple platform (Flutter, Kotlin Multiplatform, Expo) at `signInWithOAuth` ([Supabase: Login with Apple][supabase-apple]). The community Capacitor plugin `@capacitor-community/apple-sign-in` lists Android as "Not supported" ([README][community-apple]).
- **Apple's return URL never points at the app.** Apple requires the `redirect_uri` to be an absolute URL with a domain, not an IP address or `localhost`, and without a fragment ([Apple: other platforms][apple-other-platforms]), and Supabase registers its own `https://<project>.supabase.co/auth/v1/callback` there ([Supabase: Login with Apple][supabase-apple]). Apple prescribes exactly the two-hop shape for Android: its servers `form_post` to your server, and "You then redirect the custom URL scheme to give control back to the app" ([Apple: other platforms][apple-other-platforms]). Supabase Auth is that server: it always requests `response_mode=form_post` from Apple and accepts `POST` on `/callback` ([Supabase Auth source](#supabase-auth-accepts-apples-form_post)).
- **The second hop can be `audio.cup.app://auth/callback`, the URL iOS already uses.** Supabase's allow-list already holds it ([`supabase.tf`](../../../terraform/production/supabase.tf) `uri_allow_list`), and Supabase matches redirect URLs with any scheme against that list ([`IsRedirectURLValid`](#2-supabases-side-the-redirect-allow-list)). Android needs no new allow-list entry, no Apple Services ID return URL beyond the web's, and no Digital Asset Links file.
- **PKCE is already in place.** The web app creates its Supabase client with `flowType: "pkce"` and Secure Storage on Android, so `signInWithOAuth({ skipBrowserRedirect: true })` stores the verifier in the Android Keystore-backed storage and survives the app's process being killed while the browser is open; `exchangeCodeForSession(code)` reads it back, as the iOS adapter does ([PKCE](#3-pkce-verifier-storage)). PKCE is also what makes a custom scheme acceptable: an app that intercepts the redirect gets a code it cannot redeem ([RFC 8252 §8.1][rfc8252]).
- **Recommended return: Chrome's Auth Tab, in a Cup-owned Android `WebAuthentication` plugin mirroring iOS, with a Custom Tab plus a narrow custom-scheme intent filter as the fallback.** Auth Tab (androidx.browser 1.9.0+, Chrome 137+) returns the `audio.cup.app:` redirect straight to the launching activity's result callback, like `ASWebAuthenticationSession` on iOS, with an explicit cancel result ([Auth Tab guide][auth-tab], [`AuthTabIntent`][authtabintent]). Browsers without Auth Tab fall back to a Custom Tab automatically, and then the redirect arrives as an ordinary `VIEW` intent, so the manifest must also declare an intent filter for `audio.cup.app://auth/callback` ([Auth Tab guide][auth-tab]). That filter is a custom scheme, not an App Link, so it does not reopen ADR 0017. The simpler alternative, `@capacitor/browser` plus the same intent filter and `appUrlOpen`, is what Supabase's and Capgo's guides do; it works, but gives no cancel signal and routes the callback through the app's URL handling, where share intake also lives.

## 1. Apple's side: the return URL belongs to Supabase

Apple's "Incorporating Sign in with Apple into other platforms" page is Apple's own description of Sign in with Apple outside Apple platforms ([Apple: other platforms][apple-other-platforms]):

- The authorization request goes to `https://appleid.apple.com/auth/authorize` with `client_id` (a Services ID for web flows), `redirect_uri`, `response_type`, `scope`, `response_mode`, `state` and `nonce`.
- `redirect_uri` "must include a domain name and can't be an IP address or `localhost`, and must not contain a fragment identifer". The environment page adds that each registered return URL "must be absolute and must include the scheme, host, and path", with an `https://` example ([Apple: configuring your environment][apple-environment]). A custom scheme such as `audio.cup.app:` can therefore not be Apple's return URL.
- `response_mode` must be `form_post` "If you requested any scopes", that is `name` or `email`. Apple then sends an HTTP `POST` with the code to the return URL.
- Under "Return control to the app": platforms that support custom URL schemes, naming Android, "must handle the data resulting from the authorization flow by storing it on their app server in the logic of their `redirect_uri` endpoint. You then redirect the custom URL scheme to give control back to the app."

So the flow Cup would run on Android is the one Apple documents: Custom Tab or Auth Tab → Supabase `/authorize` → Apple → `form_post` to Supabase `/callback` → Supabase redirects to `audio.cup.app://auth/callback?code=…` → the app exchanges the code.

Supabase's Apple guide fits this: the Services ID's return URL is `https://<project-id>.supabase.co/auth/v1/callback`, the Services ID must be the first Client ID because Supabase uses the first one for the OAuth flow, and the six-monthly client secret rotation applies only when the OAuth flow is configured ([Supabase: Login with Apple][supabase-apple]). The Android flow is the web flow; it adds no Apple configuration of its own. The secret rotation is already in the map's "Not yet specified" list, and it applies to web sign-in anyway.

### Supabase Auth accepts Apple's form_post

In Supabase Auth (`supabase/auth`, latest release `v2.198.0` of 2026-11-16, source read on `master`), the Apple provider builds its authorization URL with `oauth2.SetAuthURLParam("response_mode", "form_post")` and requests the scopes `email` and `name` ([`internal/api/provider/apple.go`][gotrue-apple]). The router registers `ExternalProviderCallback` for both `GET` and `POST` under `/callback` ([`internal/api/api.go`][gotrue-api]). Supabase Auth keeps the OAuth state server-side in its flow state, not in a cookie, so the cross-site `POST` from `appleid.apple.com` needs no `SameSite` exception (_unverified_ on a device, but the same path serves the web flow).

## 2. Supabase's side: the redirect allow-list

`IsRedirectURLValid` in [`internal/utilities/request.go`][gotrue-request] accepts a redirect URL when it matches the site URL's scheme, host and port, or when it matches a glob in the allow-list (`URIAllowListMap`), compared without the fragment. Hostname and IP checks apply to `http` and `https` URLs; custom schemes are matched only against the list. Supabase's deep-linking guide uses custom-scheme entries such as `com.supabase://**` ([Supabase: native mobile deep linking][supabase-deep-linking]).

Cup's production allow-list is `https://cup.audio/app,https://cup.audio/app/**,audio.cup.app://auth/callback` ([`terraform/production/supabase.tf`](../../../terraform/production/supabase.tf)), and the local stack takes the same URL through [`supabase/config.toml`](../../../supabase/config.toml). The iOS adapter passes `redirectTo: "audio.cup.app://auth/callback"` ([`account-auth.ios.ts`](../../../apps/web-app/src/platform/account-auth.ios.ts)). An Android Apple flow can pass the same URL with no allow-list change.

One caveat from supabase-js `v2.119.0`: the opt-in `experimental.appendPkceFlowIdToRedirects` appends an `sb_flow_id` query parameter to `redirectTo`, and the source warns that "an extra parameter can stop exact (non-wildcard) entries from matching" ([`GoTrueClient.ts`][supabase-js-gotrueclient]). Cup does not enable it; if it ever does, the entry needs a wildcard (`audio.cup.app://auth/callback**` or similar, _unverified_ glob form).

## 3. PKCE verifier storage

[`account-session.ts`](../../../apps/web-app/src/auth/account-session.ts) creates the client with `flowType: "pkce"`, `detectSessionInUrl` from the platform (false in both shells) and `storage` from [`account-auth.native.ts`](../../../apps/web-app/src/platform/account-auth.native.ts), which is `@aparajita/capacitor-secure-storage` on Android and iOS. In supabase-js `v2.119.0`, starting a PKCE flow generates a verifier and stores it under a per-flow slot key `${storageKey}-flow-${flowId}-code-verifier`, an index under `${storageKey}-flows-code-verifier` (at most five pending flows), and, for a deprecation window, a copy under the fixed `${storageKey}-code-verifier` ([`helpers.ts`][supabase-js-helpers]). `exchangeCodeForSession(code)` without a flow ID uses "the most recently stored verifier" ([`GoTrueClient.ts`][supabase-js-gotrueclient]).

Consequences for Android:

- The verifier sits in Secure Storage, not in WebView memory, so it survives Android killing Cup's process while the browser is in front. When the redirect relaunches `MainActivity`, the web app boots, reads the verifier and can exchange the code. Delivering that callback to a fresh process is a plugin concern: with Auth Tab the activity result is redelivered to the recreated activity by the Activity Result API, and with the fallback the URL arrives as the launch intent (Capacitor's `App.getLaunchUrl()`), so the adapter must handle both (_unverified_).
- The iOS adapter's pattern carries over unchanged: `signInWithOAuth({ provider: "apple", options: { redirectTo, skipBrowserRedirect: true } })`, open the returned URL, then `exchangeCodeForSession` with the `code` from the callback.
- Side observation, not specific to Android: Cup's `clearStoredSession` removes only `ACCOUNT_SESSION_STORAGE_KEY` and `ACCOUNT_SESSION_CODE_VERIFIER_STORAGE_KEY` ([`account-session-storage.ts`](../../../apps/web-app/src/auth/account-session-storage.ts)), so the per-flow slot and index keys that supabase-js 2.119 also writes stay behind after sign-out. supabase-js caps them at five and removes a slot when it is used; whether this matters is for the spec to judge.

## 4. Android's side: getting the redirect back without App Links

[ADR 0017](../../adr/0017-keep-trial-links-out-of-the-mobile-apps.md) and [#178](https://github.com/cup-audio/cup/pull/178) removed the verified `https://cup.audio` intent filter, the `AndroidAppLinks` plugin and both `.well-known` association files, because Cup has no links meant to open the app and the association files tied every release to a signing fingerprint. ADR 0017 states that supporting links in the apps "later needs a new decision, a domain association file for each platform, and release signing set up for them again". Today the [Android manifest](../../../apps/mobile-app/android/app/src/main/AndroidManifest.xml) declares only `MAIN`/`LAUNCHER` and `SEND text/plain` on `MainActivity` (`launchMode="singleTask"`); `strings.xml` already sets `custom_url_scheme` to `audio.cup.app`, but no `VIEW` filter uses it.

### Auth Tab

Chrome's guide calls Auth Tab "a secure and simplified authentication flow for use in Android apps", supported in Chrome 137 and later, and says that "From Chrome 137, Auth Tab can directly replace existing Custom Tabs authentication integrations" ([Auth Tab guide][auth-tab]). The API, `androidx.browser.auth.AuthTabIntent`, was added in androidx.browser 1.9.0 ([`AuthTabIntent`][authtabintent]); 1.10.0 is the current stable release, of 2026-03-25 ([androidx.browser releases][androidx-browser]). Relevant details:

- `AuthTabIntent.registerActivityResultLauncher(caller, callback)` "Should be called unconditionally before the fragment or activity is created"; `launch(launcher, url, redirectScheme)` "Must be used for flows that result in a redirect with a custom scheme" ([`AuthTabIntent`][authtabintent]).
- Result codes: `RESULT_OK` "as a result of the expected redirect", with the redirect in `resultUri`; `RESULT_CANCELED` when closed without completing; the verification codes apply only to HTTPS redirects ([`AuthTabIntent`][authtabintent]).
- "For users whose devices don't support Auth Tab, fallback to Custom Tabs is automatic"; the app then receives `RESULT_CANCELED` when the Custom Tab closes, and should "handle data that can come either to your `ActivityResultCallback` or to your Activity intent" ([Auth Tab guide][auth-tab]). `CustomTabsClient.isAuthTabSupported()` tells the two apart before launch. The guide names only Chrome as supporting Auth Tab.

For a Capacitor plugin, the launcher must be registered before `MainActivity` starts; Capacitor registers plugins in `BridgeActivity.onCreate`, and its own `@ActivityCallback` mechanism launches arbitrary intents for result, so either route should work (_unverified_; a prototype should check `startActivityForResult` with `authTabIntent.intent` against `registerActivityResultLauncher`, and process-death redelivery).

### The fallback intent filter and custom-scheme risk

Android's own security guidance says that "By design, Android allows multiple apps to register intent filters for the same deep link URI", and recommends App Links and strict validation of deep-link input ([Android: unsafe use of deep links][android-deeplinks]). For an OAuth redirect, RFC 8252 accepts private-use schemes in reverse-domain form, which `audio.cup.app` is, and relies on PKCE against interception ([RFC 8252 §7.1, §8.1][rfc8252]). What remains for Cup:

- **Interception**: another app claiming `audio.cup.app` could receive the code, but cannot redeem it without the verifier in Cup's Secure Storage. With Auth Tab, the redirect never goes through intent resolution at all.
- **Injection**: any app or web page can open `audio.cup.app://auth/callback?code=…`. The handler should act only while a sign-in is pending and pass the code to `exchangeCodeForSession`, which fails for a code issued against another verifier. It must also not reach share intake, which ignores Cup links today ([`share-plugin.android.ts`](../../../apps/web-app/src/platform/share-plugin.android.ts)).
- **Task behaviour**: `MainActivity` is `singleTask`, so a `VIEW` intent arriving while the Custom Tab sits on top of Cup's task should bring `MainActivity` back to the front and clear the tab above it, delivering the intent through `onNewIntent` (_unverified_ on a device; the Capgo plugin documents `onNewIntent` handling for the same reason).

A narrow filter (scheme `audio.cup.app`, host `auth`, path `/callback`) keeps every other `audio.cup.app:` URL out of the app, and does not make Cup claim any web link, so ADR 0017's decision stands. The iOS Share Extension's `audio.cup.app://share` handoff is iOS-only and unaffected.

## 5. How comparable apps do it

- **Supabase's own guidance**: Flutter and Kotlin Multiplatform use `signInWithOAuth` with a deep-link redirect on Android; the deep-linking guide shows a `VIEW`/`DEFAULT`/`BROWSABLE` filter with `android:scheme` and `android:host`, and an Expo example that opens the URL with `openAuthSessionAsync` and `skipBrowserRedirect: true` ([Supabase: Login with Apple][supabase-apple], [Supabase: native mobile deep linking][supabase-deep-linking]).
- **`@capgo/capacitor-social-login`** (8.7.11, 2026-11-13): its Android Apple provider opens a Custom Tab ([`AppleProvider.java`][capgo-apple-provider]) and receives the redirect as a custom-scheme intent through a modified `MainActivity`'s `onNewIntent`, treating an activity resume without a redirect as cancellation. Its Supabase recipe does not use Supabase's built-in Apple callback: Apple's return URL is a Supabase Edge Function that exchanges Apple's code and redirects to the app with Apple's ID token, which the app then hands to Supabase ([Capgo: Supabase Apple on Android][capgo-supabase-apple]). That needs Cup to host Apple's client secret in an extra function and makes Android sign in differently from the web; with Supabase's own callback and PKCE available, Cup gains nothing from it.
- **`@capacitor-community/apple-sign-in`**: iOS and web only ([README][community-apple]).

## Open points for the spec

- Whether the Android Apple button opens Auth Tab through a Cup plugin (option A) or `@capacitor/browser` (option B), and how the adapter reports cancellation in each.
- A prototype on a device: Auth Tab on Chrome 137+, the Custom Tab fallback with another default browser, process death while the tab is open, and the `singleTask` return.
- The mobile E2E suite: the fake auth provider can redirect to `audio.cup.app://auth/callback` as it does for iOS, but Auth Tab and Custom Tabs drive a real browser on the emulator.
- Account chooser and fresh sign-in semantics for Apple (map item "Fresh authentication with Apple").
