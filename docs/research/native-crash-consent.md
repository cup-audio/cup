Whether a specific setup counts as "strictly necessary" is a judgement no regulator has made for crash reporting, so a lawyer should confirm whichever option the operator picks.

## Question

How do companies that ship native apps to listeners in the EU, above all in Germany and Austria, run crash reporting that stores an identifier on the device? Is there a defensible way for Cup's Android and iOS shells to run native crash capture without explicit consent, given that Sentry's native SDKs write an `INSTALLATION` file with a random UUID on first start ([#367](https://github.com/patricktree/cup/issues/367)) and [#341](https://github.com/patricktree/cup/issues/341) decision 1 avoided a consent banner by storing no telemetry-only identifier?

## Answer

**No regulator or court has said that crash reporting is "strictly necessary", and the strictest readings say it is not.** The consent exemption in ePrivacy Art. 5(3), § 25 Abs. 2 Nr. 2 TDDDG and § 165 Abs. 3 TKG 2021 covers storage or access that is strictly necessary to provide the service the user explicitly asked for. The Article 29 Working Party named "product improvement and debugging" among purposes that are not related to a requested service, and held that first-party analytics are not exempt because the site works without them. The German supervisory authorities read "unbedingt erforderlich" as technical necessity for the requested function. The most a provider can lean on is the DSK's statement that components keeping the basic service "sicher, schnell und stabil" can be attributed to it, and that "die fehlerfreie Auslieferung" can be covered by the user's wish ([Legal position](#legal-position)).

**Leaving out the identifier does not take crash reporting out of scope; it only makes the exemption argument stronger.** The EDPB counts reading device information through an SDK as "gaining access", and counts any storage, including in RAM and however briefly, as "storage". A native crash report is written to disk at the crash and sent on the next launch, so native crash capture always involves storage and access. What separates the options is how convincingly each passes the strict-necessity test, and a persistent installation ID used to count crash-free users is the weakest part, because the DSK says unique identifiers are only rarely strictly necessary ([Storage, access and the identifier](#storage-access-and-the-identifier)).

**The same reasoning applies to the JS telemetry Cup already runs without consent.** It too reads device information through code Cup ships, so decision 1 of #341 rests on the strict-necessity exemption and on minimal intrusion, not on being out of scope. Native crash capture without a persistent identifier is the same kind of processing plus an on-disk crash cache; native capture with the `INSTALLATION` file adds the element the authorities single out ([Consequence for #341](#consequence-for-341)).

Options, ranked from "no consent needed, most defensible" to "consent needed":

| Rank | Option                                                                                                                | Consent from Cup                                                                                 | What Cup gets                                                         | Main cost                                                                                                                                                                   |
| ---- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | [Store-side crash reports](#store-side-baseline): Play Console Android vitals, Xcode Organizer and App Store Connect  | None: Cup ships no code that stores or reads anything; Google and Apple ask the user at OS level | Native crash and ANR stack traces, crash rates per device and version | Only from users who share diagnostics with developers, Play installs only on Android, no WebView or JS context, delay                                                       |
| 2    | JS-only shells (`enableNative: false`)                                                                                | None, on the same footing as #341 decision 1                                                     | Everything inside the WebView, as on the web                          | No native crashes, ANRs, app hangs or native offline cache (rank 1 covers native crashes in aggregate)                                                                      |
| 3    | [Native capture with the installation ID kept in memory](#keeping-the-installation-id-in-memory), native sessions off | None, if the operator accepts the § 25 Abs. 2 Nr. 2 argument: defensible but contested           | Native crashes, ANRs, app hangs with JS context                       | Crash reports and the scope cache still sit on disk until sent; Android hook relies on an SDK internal; iOS has no hook, only an unverified workaround; no crash-free users |
| 4    | Native capture as shipped (persistent `INSTALLATION` file), no consent                                                | Needed by the strict reading; the ID serves statistics, not fixing the crash                     | Full Sentry native, including release health                          | Contradicts #341 decision 1; weakest exemption argument                                                                                                                     |
| 5    | Native capture after opt-in: a settings toggle or a one-time prompt, initialising the native SDK only after a yes     | Yes, and nothing else is needed                                                                  | Full Sentry native for the users who agree, including release health  | A prompt or toggle to design; fewer reports; the native SDK must not start before the yes                                                                                   |

**Other apps split between rank 4 and rank 5.** ORF names Sentry error and performance monitoring as running only "Wenn Sie Ihre Zustimmung dafür erteilt haben"; Firefox for Android never sends a crash report without the user confirming it; Bitwarden ships Crashlytics switched on, with an in-app toggle to turn it off; ARD Sounds (formerly ARD Audiothek) lists Firebase Crashlytics "zur Ermittlung von App-Abstürzen" as part of its technical infrastructure with no consent; Spotify bases troubleshooting on contract performance with no opt-out; Signal ships no crash SDK and relies on debug logs the user submits ([Practice](#practice)).

**Recommendation for Cup** (see [Recommendation](#recommendation)): turn on the store-side reports now (rank 1); run the shells JS-only by default (rank 2), which keeps #341 decision 1 exactly; and start Sentry's native SDK only after an explicit opt-in (rank 5), which matches the operator's lean and ORF's practice. Rank 3 is the most defensible way to run native capture without consent, and is worth it only if the operator accepts a contested exemption argument and the device checks in [Needs confirmation](#needs-confirmation) pass.

## Legal position

### The exemption and its wording

Art. 5(3) of the ePrivacy Directive, as amended by Directive 2009/136/EC, requires consent for storing information or gaining access to information already stored in the terminal equipment, except for "technical storage or access for the sole purpose of carrying out the transmission of a communication" or where "strictly necessary in order for the provider of an information society service explicitly requested by the subscriber or user to provide the service" ([consolidated text](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:02002L0058-20091219)).

Germany transposes it in [§ 25 TDDDG](https://www.gesetze-im-internet.de/ttdsg/__25.html): Abs. 1 requires consent based on clear and comprehensive information, and Abs. 2 Nr. 2 exempts storage or access that is "unbedingt erforderlich" so that the provider can deliver a "vom Nutzer ausdrücklich gewünschten digitalen Dienst".

Austria transposes it in [§ 165 Abs. 3 TKG 2021](https://www.ris.bka.gv.at/NormDokument.wxe?Abfrage=Bundesnormen&Gesetzesnummer=20011678&Paragraf=165). Its wording differs: it obliges providers to inform users about the personal data they process, makes the "Ermittlung dieser Daten" subject to active consent, and then says this does not prevent technical storage or access that is "unbedingt erforderlich" for a service the user explicitly requested. Inference: the Austrian text ties consent to collecting personal data, which reads narrower than the Directive's "information"; an interpretation in conformity with the Directive would likely close that gap, so Cup should not rely on it. The Austrian DSB's cookie FAQ, which the DSK cites as "Stand 20.12.2023", could not be retrieved during this research (`dsb.gv.at` refused connections), so its position is not quoted here.

### Article 29 Working Party, Opinion 04/2012

[Opinion 04/2012 on cookie consent exemption (WP 194)](https://ec.europa.eu/justice/article-29/documentation/opinion-recommendation/files/2012/wp194_en.pdf) sets two tests for criterion B: the user did "a positive action to request a service with a clearly defined perimeter", and the storage is strictly needed so that "if cookies are disabled, the service will not work". It reads the service as a sum of functionalities, each of which must be requested.

In its section on third-party advertising, the Working Party lists operational purposes that cannot be exempt, among them "product improvement and debugging", because none of them is "related to a service or functionality of an information society service explicitly requested by the user". The context is advertising cookies, but the reasoning is about the purpose. First-party analytics fail too, because "the user can access all the functionalities provided by the website when such cookies are disabled", although the Working Party thought them low-risk when aggregated, disclosed, anonymised and paired with a user-friendly opt-out, and suggested the legislator might add an exemption for them. Inference: crash reporting fails the "service will not work" test in the same way, since the app works without a crash reporter; the low-risk remarks support an opt-out design but are not an exemption.

### EDPB Guidelines 2/2023 on the technical scope of Art. 5(3)

[Version 2.0, adopted 7 October 2024](https://www.edpb.europa.eu/system/files/documents/2024-10/edpb_guidelines_202302_technical_scope_art_53_eprivacydirective_v2_en_0.pdf), says what is in scope and expressly does not analyse the exemptions (paras. 40 and 56). The points that matter for crash reporting:

- **Reading device information is access.** Consent "also applies when a read-only value is accessed", whoever stored it, including the device manufacturer (paras. 11–12, 31). Instructing the device through an SDK to send stored information "triggers the applicability of Article 5(3)" (para. 34), and so does sending back results of local processing (para. 53).
- **Any storage counts, in any medium, for any duration.** There is no lower limit on how long information persists (para. 37), and RAM and CPU cache are not excluded (para. 38).
- **Applicability is not a consent requirement.** Each case must be checked against the exemptions (para. 56).

Inference: under this reading, a crash reporter that reads the device model and OS version and writes a crash report to disk is in scope whether or not it stores an identifier, and so is Cup's JS telemetry. The exemption, not the scope, decides.

### German DSK, OH Digitale Dienste (Version 1.2, November 2024)

The [Orientierungshilfe für Anbieter:innen von digitalen Diensten](https://datenschutzkonferenz-online.de/media/oh/OH_Digitale_Dienste.pdf) is the German authorities' reading of § 25 TDDDG. It contains no statement on crash reporting by name. What bears on it:

- **Apps are covered, and reading device information is access.** Outside websites, "automatische Update-Funktionen" can trigger the consent requirement, and reading hardware IDs and similar on mobile devices is named (Rn. 22); actively reading device properties with code and sending them to a server is access (Rn. 24); no personal reference is needed (Rn. 26).
- **The requested service is read granularly from the user's view.** Every digital service has a "Basisdienst", which "wird oft von Komponenten flankiert, damit dieser sicher, schnell und stabil zur Verfügung gestellt werden kann"; systems for user-oriented fraud prevention and IT security can be attributed to it (Rn. 74). General functions such as measuring visitor numbers are not per se part of it; it depends on whether their specific purposes are user-oriented (Rn. 77).
- **"Unbedingt erforderlich" means technical necessity.** Only access that is technically required to provide the requested service is exempt, never what the business model needs (Rn. 78), minimised in time, content, duration and recipient (Rn. 79, 95).
- **Unique identifiers rarely qualify.** Processes that assign unique identifiers are the ones to question, because they intrude most; strict necessity exists "nur in wenigen Fällen" for them (Rn. 81). Recurring use can only be assumed for services that require sign-in (Rn. 80).
- **Purpose decides, and error-free delivery can be part of the wish.** Reach analysis serves many purposes, among them "Fehlfunktionen zu erkennen"; "Die fehlerfreie Auslieferung der Webseite kann beispielsweise vom Nutzerwunsch umfasst sein", while advertising economics serves only the operator (Rn. 90).

Inference: Rn. 74 and Rn. 90 are the strongest official hooks for exempting crash capture that serves only fixing failures in the service the user uses, with nothing stored beyond what the report needs. Rn. 78 and Rn. 81 cut against a crash reporter that keeps a persistent per-installation ID, whose purpose (counting affected users, crash-free users) is statistical.

The Bavarian authority's [app audit sheet](https://www.lda.bayern.de/media/pruefungen/App_Informationsblatt.pdf) (Stand 22.12.2023) says apps, like websites, "bedürfen ... im Regelfall einer Einwilligung" when they access the terminal, for example by reading device identifiers, points to EDPB 2/2023 for the scope, and leaves later processing to Art. 6 GDPR.

### CNIL, recommendation on mobile applications

The [CNIL recommendation](https://www.cnil.fr/sites/cnil/files/2025-05/recommendation-mobiles-app.pdf) (deliberation 2025-024 of 27 March 2025, replacing the July 2024 version) lists, as examples of exempt read or write operations, functionality the user requested, securing the service with a focus on protecting the user, and limited audience measurement such as "simple counting of the number of daily users for the purpose of sizing the service". Crash reporting is not among them. It names "reading a technical identifier of the user's terminal for diagnostic and/or telemetry purposes" as something an SDK provider is a controller for when it does so for its own purposes. For OS providers, it recommends a crash reporting system "in accordance with the principle of minimization ... including consent to the reporting of the crash", and inviting publishers to obtain consent "(where necessary)" before each retrieval of bug and crash data. Inference: the CNIL treats consent for crash reports as the default good practice, without saying it is always required.

### Courts, and where the law is moving

No court decision on crash reporting, Crashlytics or diagnostic SDKs under § 25 TDDDG, § 165 TKG or Art. 5(3) turned up. The CJEU's [Planet49 judgment (C-673/17)](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:62017CJ0673) established that Art. 5(3) protects any information in the terminal, personal or not, and requires active consent; the EDPB quotes it at para. 10.

The UK, outside the EU, has since written the missing exemption into law: the [Data (Use and Access) Act 2025, Schedule 12](https://www.legislation.gov.uk/ukpga/2025/18/schedule/12/enacted), lists storage or access "to prevent or detect technical faults in connection with the provision of the service requested" as strictly necessary (new Schedule A1, para. 4(2)(d)). It has no force in the EU, but shows a legislator found the point needed stating.

In the EU, the Commission's Digital Omnibus proposal [COM(2025) 837](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=celex:52025PC0837) would move terminal-equipment rules for personal data into a new Art. 88a GDPR with exemptions that, according to law-firm summaries, cover security and aggregated first-party audience measurement. The proposal text could not be retrieved during this research, the Council position is still moving according to [secondary reporting](https://ppc.land/digital-omnibus/), and nothing of it applies today. Cup should not plan on it.

### Storage, access and the identifier

Native crash capture involves four distinct operations, and they fare differently under the exemption test:

| Operation                                                     | In scope (EDPB)             | Strict-necessity argument                                                                      |
| ------------------------------------------------------------- | --------------------------- | ---------------------------------------------------------------------------------------------- |
| Reading device model, OS version, memory at the crash         | Yes, access (paras. 11, 34) | Moderate: needed to fix the crash; minimise to what diagnosis needs                            |
| Writing the crash report to disk until the next launch        | Yes, storage (paras. 35–38) | Moderate: a crash kills the process, so a report can only be sent from disk; deleted once sent |
| Persisting the scope (account ID, breadcrumbs) to enrich ANRs | Yes, storage                | Weak to moderate: a telemetry copy of an ID the app already holds                              |
| A persistent per-installation UUID                            | Yes, storage                | Weak: it counts users and links reports across launches; DSK Rn. 81                            |

The processing of the report after it reaches Cup, in Sentry, is a separate question under the GDPR, where legitimate interest (Art. 6(1)(f)) works for crash diagnostics, as #341 assumed for all telemetry. The Bavarian sheet states the same split: § 25 TDDDG for the access, Art. 6 GDPR for what follows.

### Consequence for #341

Decision 1 of #341 says the ePrivacy line is kept "by storing no telemetry-only identifier on the device". Under EDPB 2/2023, the JS telemetry in the shells and on the web is still in scope (it reads device properties and keeps trace IDs in memory), so its lawfulness without consent depends on § 25 Abs. 2 Nr. 2 TDDDG and § 165 Abs. 3 TKG. Inference: the "no identifier" rule is a minimisation that makes the strict-necessity argument plausible (DSK Rn. 79, 81), not an exit from the provision. That does not make #341 wrong, but the privacy policy and the decision record should state the exemption as the basis, rather than "nothing is stored".

## Keeping the installation ID in memory

### Android (sentry-java 8.64.0): a pre-set static field

`Installation.id(context)` returns the static field `deviceId` when it is set, and only otherwise reads or writes `files/INSTALLATION` ([`Installation.java` L18, L36–L51](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/Installation.java#L18-L51)). Every caller goes through that method: the distinct ID at init ([`AndroidOptionsInitializer.java` L546–L551](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/AndroidOptionsInitializer.java#L546-L551)), `user.id` on events ([`DefaultAndroidEventProcessor.java` L178, L376](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/DefaultAndroidEventProcessor.java#L178)), the device context ([`DeviceInfoUtil.java` L488](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/DeviceInfoUtil.java#L488)), ANR and exit-info events ([`ApplicationExitInfoEventProcessor.java` L702](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/ApplicationExitInfoEventProcessor.java#L702)) and the hybrid SDK bridge ([`InternalSentrySdk.java` L105](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/InternalSentrySdk.java#L105)).

The field is package-private, non-final and annotated `@TestOnly`. A small class in Cup's Android app placed in the package `io.sentry.android.core` can therefore set `Installation.deviceId` to a fresh random UUID before Sentry starts, and the file is never written. The timing works: `@sentry/capacitor` disables Sentry's auto-init ([plugin manifest](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/android/src/main/AndroidManifest.xml)) and starts the native SDK only when JS calls `initNativeSdk` ([`SentryCapacitor.java` L73–L76](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/android/src/main/java/io/sentry/capacitor/SentryCapacitor.java#L73-L76)), long after `MainActivity.onCreate`. No library patch is needed. The cost: it depends on an SDK internal that a Sentry update can rename or remove, so a test should assert that `files/INSTALLATION` stays absent after an upgrade.

Two Android settings can be changed without patching the plugin, because `SentryAndroid.init` applies manifest `<meta-data>` before the plugin's configuration callback ([`SentryAndroid.java` L137–L155](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/SentryAndroid.java#L137-L155)), and the plugin only overrides `enableAutoSessionTracking` when JS passes it ([`SentryCapacitor.java` L112–L114](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/android/src/main/java/io/sentry/capacitor/SentryCapacitor.java#L112-L114)), which `FilterNativeOptions` never does ([`nativeOptions.ts` L18–L51](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/src/nativeOptions.ts#L18-L51)):

- `io.sentry.auto-session-tracking.enable=false` turns off native sessions on Android ([`ManifestMetadataReader.java` L71](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/ManifestMetadataReader.java#L71)). This is a cheaper route than the `pnpm patch` #367 proposed, for Android only.
- `io.sentry.enable-scope-persistence=false` stops the SDK from writing the scope, including `user.json` with the account ID, to `.scope-cache` ([`ManifestMetadataReader.java` L157, L606–L608](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/ManifestMetadataReader.java#L606-L608); [`PersistingScopeObserver.java` L52–L53](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry/src/main/java/io/sentry/cache/PersistingScopeObserver.java#L52-L53)). The cost: ANRs and crashes reported on the next launch lose the user, breadcrumbs and tags of the session that died.

### iOS (sentry-cocoa 9.28.0): no hook

`SentryInstallation.id(withCacheDirectoryPath:)` keeps IDs in a private static dictionary and, on a miss, reads `INSTALLATION` from the cache directory or creates it with a new UUID ([`SentryInstallation.swift` L11–L42](https://github.com/getsentry/sentry-cocoa/blob/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Swift/Helper/SentryInstallation.swift#L11-L42)). The client warms it at start ([`SentryClient.m` L182–L184](https://github.com/getsentry/sentry-cocoa/blob/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Sentry/SentryClient.m#L182-L184)). There is no setter, the dictionary is Swift `private`, and the cache directory defaults to `Library/Caches` ([`Options.swift` L715–L720](https://github.com/getsentry/sentry-cocoa/blob/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Swift/Options.swift#L715-L720)) and is not forwarded by the plugin. The Capacitor plugin links prebuilt binaries (`sentry-apple-binaries`), so a source patch means building sentry-cocoa from source.

An unverified workaround: before Sentry starts, the app creates a directory named `INSTALLATION` at `Library/Caches/INSTALLATION` on every launch. Reading it as a file then yields no data, `createFile` fails and logs an error, and the SDK keeps the new UUID in its dictionary only, per process. Inference from the code above; it needs a device test, and an empty directory is still a (non-identifying) write. The scope is persisted on iOS too, for watchdog-termination reports (`SentryScopePersistentStore+User.swift` in [`Sources/Swift/Persistence`](https://github.com/getsentry/sentry-cocoa/tree/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Swift/Persistence)), and no forwarded option turns that off.

### What breaks, and what stays on disk

- **Release health.** With a fresh ID per launch, "crash-free users" counts every launch as a new user. With native sessions off, as #367 recommends, there are no native sessions at all. Play Console's user-perceived crash rate, per daily active user, is a substitute ([Android vitals](https://developer.android.com/topic/performance/vitals)).
- **Linking reports across launches.** A crash reported on the next launch carries the new launch's ID, not the crashed one's. Since #367 sets `user.id` to the account ID or `signed-out`, this changes little.
- **The crash cache stays.** sentry-java writes envelopes, `session` files and `last_crash` markers under `cache/sentry` ([`AndroidOptionsInitializer.java` L573–L575](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/AndroidOptionsInitializer.java#L573-L575), [`EnvelopeCache.java` L64–L71](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry/src/main/java/io/sentry/cache/EnvelopeCache.java#L64-L71)), and sentry-cocoa stores "events, transactions, profiles, raw crash data" in its cache directory. A process that has crashed can only report from disk on the next launch; ANRs are found from Android's `ApplicationExitInfo` on the next launch. This cache is storage under EDPB para. 37 and must stand on the strict-necessity argument; no SDK avoids it.

## Store-side baseline

**Android vitals** collect stability data "When a user allows it", on the device, and Google Play shows it in the Play Console; vitals include crashes before any SDK starts, but come only from "users who agreed to share data", certified devices and Play installs, and are shown only when there is enough data to report anonymously ([Android vitals](https://developer.android.com/topic/performance/vitals)).

**Xcode Organizer and App Store Connect** present crash reports "from customers who share diagnostic and usage information", and TestFlight users share them automatically; watchdog, jetsam and thermal events are not in the Crashes organizer ([Acquiring crash reports and diagnostic logs](https://developer.apple.com/documentation/xcode/acquiring-crash-reports-and-diagnostic-logs)).

Inference: Cup ships no code that stores or reads anything for these reports; the OS vendor collects them under its own device-level choice. That makes them the one crash source that needs no consent from Cup. They see native crashes in the shell, plugins and WebView host, but not JS errors or Cup's context.

**MetricKit is not part of that baseline.** It delivers crash and hang diagnostics to the app itself ("Diagnostic reports arrive immediately in iOS 15 and later", [MetricKit](https://developer.apple.com/documentation/metrickit)), and Android's `ApplicationExitInfo` does the same for exit reasons. If Cup's code reads those reports and sends them to Sentry, that is "gaining access to information already stored" (EDPB para. 53), so it stands on the same exemption argument as rank 3, minus Sentry's own files. Whether MetricKit delivers only for users who share analytics with developers was not stated in the documentation read.

## Recommendation

1. **Turn on the store-side reports now** (rank 1): upload dSYMs and R8 mapping files with each release so Play Console and Xcode Organizer show symbolicated native stack traces. This needs no consent and no code.
2. **Run the shells JS-only by default** (`enableNative: false`, rank 2). It keeps #341 decision 1 exactly and loses only native crashes, which rank 1 covers in aggregate.
3. **Start the native SDK only after an opt-in** (rank 5): one switch ("Absturzberichte senden") in settings, optionally offered once after sign-in, with JS calling `Sentry.init` with `enableNative: true` only when it is on, and native sessions and the `INSTALLATION` file then acceptable because the user agreed. Withdrawing consent must stop the native SDK and delete its files (`cache/sentry`, `files/INSTALLATION`, `.scope-cache` on Android; the Sentry files in `Library/Caches` on iOS). This matches the operator's lean and what ORF does. The consent itself has to be stored on the device, which DSK Rn. 84 accepts without a UID.
4. **If the operator wants native capture without consent, use rank 3, not rank 4,** and treat it as a documented legal judgement under § 25 Abs. 2 Nr. 2 TDDDG and § 165 Abs. 3 TKG, supported by DSK Rn. 74 and Rn. 90 and contradicted by WP 194 and DSK Rn. 78. Then: keep the installation ID in memory (Android field, iOS directory workaround if it holds), sessions off, scope persistence off on Android, report content minimised by #367's `beforeSend` and scrubbing rule, an opt-out switch in settings as WP 194 expects for low-risk analytics, and the privacy policy naming crash diagnostics and the exemption.

Uncertainties, in order of weight: no regulator or court has ruled on crash reporting under the strict-necessity exemption; EDPB 2/2023 counts RAM as storage, which, read literally, puts even in-memory IDs in scope; the Austrian DSB's current view could not be read; the Android hook depends on an SDK internal and the iOS one on an untested filesystem trick.

- On a device: a directory at `Library/Caches/INSTALLATION` keeps sentry-cocoa from writing the file, without breaking start-up or event sending.
- The Android manifest keys `io.sentry.auto-session-tracking.enable` and `io.sentry.enable-scope-persistence` take effect under `@sentry/capacitor` 4.6.0.
